# x86-64: QEMU faults too — the divergence is after the repair, and it is `kernel_gs_base`

**Status: MEASUREMENT. The brief's premise is corrected with QEMU's own log: QEMU **does** take the
direct-map fault, on the same instruction, on the direct map of *its own* `boot_params`. Both repair
it; both then take the same branch; and the difference is that on hardware `MSR_KERNEL_GS_BASE` is
**not 0**, so the `swapgs` is harmless — while on the port it is 0 and the swap zeroes `GS.base`.
No fix is claimed: the write that should set it is in main `.text` (later than this point), so the
next step is to find whether hardware's early path executes one that the port misses.**

Every claim is tagged **MEASURED** / **READ** / **INTERPRETATION** / **PROJECTION**.

---

## 1. QEMU's register state at the same point (MEASURED)

QEMU's own `-d int` log (same image, `-m 256`, `earlyprintk=serial nokaslr`, so its addresses are
link addresses — its slide is 0), first exception:

    qemu: 0: v=0e e=0000 i=0 cpl=0 IP=0010:ffffffff83077246 pc=ffffffff83077246 \
             SP=0000:ffffffff82a03f30 CR2=ffff888000014790

* **the same instruction** as the port (`0xffffffff83077246`, `copy_bootdata`'s `rep movsd`),
  `e=0000`, `cpl=0`;
* **`CR2 = 0xffff888000014790`** — the *direct map of QEMU's own* `boot_params`, physical
  **0x14790** (the port's is 0x84790). So **QEMU faults on this access too**;
* QEMU then takes three more demand #PFs (`0xffffffff8309c396`, `0xffffffff8309c3b3`,
  `0xffffffff819eb952`), **never faults at `pc=ffffffff81c0123a`** (the `%gs:0x19000` read: zero
  hits), and boots to the banner.

**So the fault is not the divergence, and the "inside vs outside the mapped range" arithmetic the
brief proposed is not the axis either:** both `boot_params` addresses (0x14790, 0x84790) are in low
memory, inside the range the early fixup identity-maps — and in any case the direct map is
**demand-built** (`do_early_exception` → `early_make_pgtable`), so a first touch faulting is normal
on both.

## 2. The call site is the same on both (MEASURED + READ)

`x86_64_start_kernel`'s unconditional `copy_bootdata` (link `0xffffffff83077608`) runs **before**
`x86_64_start_reservations`' guarded one (`0xffffffff83077555`) on any boot, so the first direct-map
access — and therefore the first fault — is from that same call on both machines:

* **MEASURED on the port**: `V86C_BREAK` on both sites hits only `0x8ae77608`; the guarded site is
  never reached (`results/x86-64-branch.md`);
* **MEASURED on QEMU**: its fault-0 `SP = 0xffffffff82a03f30` equals the port's `rsp` at the same
  instruction, de-slid (`0xffffffff8a803f30 - 0x7E00000`), exactly.

So the return address at the slot the kernel's return path tests is `0x…8307760d` on **both** — bit 2
of `0x0d` **set** — and **the `swapgs` branch is taken on hardware too**.

## 3. What that leaves: `MSR_KERNEL_GS_BASE` (MEASURED)

    port, at the swapgs:  gs_base = 0xffffffff8ae42000   kernel_gs = 0x0

The swap therefore sends `GS.base` to 0, the next `%gs:0x19000` resolves to the bare `0x19000`,
`early_make_pgtable(0x19000)` computes `physaddr = 0x19000 - 0xffff888000000000` (wrapped,
`>= MAXMEM`) and refuses, the kernel panics, and the third nested fault trips
`early_recursion_flag > 2`, which halts silently.

**QEMU survives the same `swapgs`**, so on hardware `kernel_gs ≠ 0` at that instant. And the kernel
*does* write MSR `0xC0000102` — **30 sites**, encoded `mov edi,0xc0000102; call wrmsr` (my earlier
search for `mov ecx,0xc0000102` found none because the encoding differs: `bf 02 01 00 c0` then a
call). **All 30 are in main `.text`**, i.e. later than this point in program order.

**INTERPRETATION:** either one of those sites *is* reached before the fault on hardware (through the
early call tree of `x86_64_start_kernel`: `sme_early_init`, `kasan_early_init`,
`idt_setup_early_handler`, `tdx_early_init` — all main-text functions), and the port misses it; or
hardware's slot value differs after all and §2's argument has a hole. The first reading is the one
the evidence supports, and it is testable with the toolkit already in place.

## 4. The next fork, instrumented

`V86C_BREAK` on the `mov edi,0xc0000102` sites that lie in the early call tree (link
`0xffffffff81030e89`, `0xffffffff81030edf`, `0xffffffff81030fab`, `0xffffffff81031376`,
`0xffffffff8104a690`, … → runtime `+0x7E00000`), with the port's own `wrmsr` handler
(`src/cpu/instructions_0f.c:6452`) as the reader: if any of them executes before the `swapgs`, the
port has a `wrmsr` defect; if none does, hardware must reach one that the port skips, and the ring at
that point names where.

**The calibrated target is NOT reached**: no first `printk`, so nothing was added to
`gate-x86-64.sh`.
