# X86-64-S6 — the ALU family at 64 bits

**Unit:** `HANDOFF=v86c-x86-64-s6`, slice **S6** of `results/x86-64-plan.md` (§6's S6 row:
"add/adc/sub/sbb/and/or/xor/cmp/test/inc/dec/neg/not, the `WRAP` bodies over the widened cores,
plus the sign-extension boundaries"; corpus family 2; rung coder). S0-S5 are landed
(`results/x86-64-s0.md`, `-s1-s2.md`, `-s3.md`, `-s4.md`, `-s5.md`); S7-S13 are untouched.

**The claim, one sentence:** the eleven 64-bit ALU operations this slice names now deliver their
results **and their flags** through the port's ONE set of flag cores at `OPSIZE_64`, and **9 of
family 2's 10 cases are green against the host CPU** — the tenth needs `DIV`, which is S8's, and
is RED **by name**. While doing it, the slice found and fixed a live 64-bit defect in the shared
logic cores (`arith_and/or/xor` took `int32_t` operands), and it found that family 2's own
instrument was **comparing a bit it does not own** (§6).

Claims are tagged **MEASURED** (run on this host in this pass, the command or artifact named),
**READ** (from source, `file:line`) or **INTERPRETATION**. The shipped binary moved from
`4d922c7a…` (S5 round 2) to **`3a6b7694…`** (MEASURED, `sha256sum build/v86c`), so every gate
below ran against S6 bytes.

`ctrl-jcc-64` and `ctrl-setcc` (S7's family) had their flag producers missing — a `cmp`/`test` at

## 3. The flag rules, and where each one is verified

There is **no second flag path**: every body calls `arith.h`'s wrappers, which call the S1-widened
`flags_add/adc/sub/sbb/inc/dec` (int64_t operands, `OPSIZE_64`, the canonical zero-extended
`last_op*` storage, `getcf` masking both operands) and the now-widened `arith_and/or/xor`. The
plan's phrase for this slice is "the `WRAP` bodies over the widened cores", and the wrappers are
literally that: `int64_t add64(int64_t x, int64_t y) { return flags_add(x, y, OPSIZE_64); }`.

| flag | rule | verified by |
|---|---|---|
| **CF** | carry out of bit 63 (`flags_add`'s `dest > mask - src` shape at the operand width); `sub/sbb` borrow; **inc/dec preserve it** | `alu-add64-carry-chain`, `alu-adc-chain-wide`, `alu-sub-sbb-64`, `alu-inc-dec-64` |
| **OF** | signed overflow at bit 63; `neg`'s `0x8000000000000000` corner | `alu-inc-dec-64`, `alu-sign-boundary-32-64`, `alu-neg-not-64` |
| **SF** | bit 63 of the result | `alu-test-cmp-64`, `alu-sign-boundary-32-64`, `alu-logic-64` |
| **ZF** | result == 0 at the operand width | `alu-test-cmp-64`, `alu-logic-64` |
| **AF** | carry out of bit 3 (the same rule at every width) | `alu-sign-boundary-32-64`, `alu-add64-carry-chain` |
| **PF** | low byte parity | every case that stores a flags word |
| the **32-vs-64 boundary** | a 32-bit destination zero-extends into the 64-bit register, a 64-bit one does not | `alu-op32-vs-op64` (the case exists for this line) |
| **NOT sets no flags** | the SDM leaves the arithmetic flags alone | `alu-neg-not-64` |
| **adc/sbb read CF first** | `flags.h`'s invariant, which `flags_adc/sbb` implement | the two chain cases |

## 4. What landed

`src/cpu/arith.c`/`.h`: **the three logic cores widened to `int64_t`** (§5.1) and thirteen 64-bit
wrappers (`add64/adc64/sub64/sbb64/cmp64/inc64/dec64/neg64/not64/and64/test64/or64/xor64`).

`gen/x86_table64.js`: nineteen new overlay entries — the two-operand forms `0x01/03/09/0B/11/13/
19/1B/21/23/29/2B/31/33/39/3B`, `0x85` (test), `0x83` (the imm8 group, all eight sub-ops),
`0xF7` (of which `/2` not and `/3` neg are bodies) — and `0xFF` gained bodies for `/0` inc and
`/1` dec while `/2../6` (call/callf/jmp/jmpf/push) stay S7's **named stops**, which the
availability scan produces automatically for a sub-op with no body.

`src/cpu/instructions_64.c`: **58 bodies**: the sixteen two-operand pairs + `test` (34), the 0x83
group's sixteen, `0xF7 /2` and `/3` (4), `0xFF /0` and `/1` (4), and — the one that is not ALU —
**`0x8F /0` `pop r/m64`**, which family 2's cases need to store RFLAGS into the compared window.
The four `INSTR64_ALU_IS_S6` stops are **gone** (S5 round 2's seat is filled).

## 5. Defects and instrument problems this slice found

### 5.1 The logic cores truncated 64-bit operands (LIVE, silent-wrong)

`arith_and/or/xor` were `static int32_t arith_and(int32_t dest_operand, int32_t
source_operand, int32_t op_size)` — so a 64-bit `and rdx, rcx` would have been computed on the
**low 32 bits of both operands** and stored as if it were the 64-bit result, with `set_last_result`
faithfully masking a value that was already destroyed. MEASURED as the case that catches it:
`alu-logic-64` (`0xF0F0F0F0F0F0F0F0 & 0x0F0F0F0F0F0F0F0F`). Fixed by widening the three cores;
the 8/16/32-bit wrappers truncate on the way back and are bit-identical — pinned by the M0
transcript and by `make nasm`'s 118/118.

### 5.2 `pop r/m64` (0x8F /0) was the missing plumbing

Nine of family 2's ten cases store RFLAGS with `pushfq; pop qword ptr [slot]`, and `0x8F /0` was
a default-64 **named stop** (S5's shutter). Implementing it was necessary for the slice's own
instrument; it is named in the report rather than passed off as S6's subject.

### 5.3 The reference's `custom_modrm_resolve` shape, measured the hard way

`0x8F` is `custom_modrm_resolve` in v86's table, so the emitter passes the **raw modrm byte** where
the ordinary form passes a resolved address — and the first version of the body treated it as an
address. MEASURED: `alu-logic-64`'s RAX came out `0x100080` (an address) with the flags word
written into physical 4. The body now resolves the address itself **in the reference's order**
(`instructions.c`'s `instr32_8F_0_mem`: the stack pointer is updated *before* the address is
resolved, restored for the read, and applied after the write).

### 5.4 The instrument compared a bit it does not own (IF)

Every flags word was compared **unmasked** in memory, and the two legs run at different privilege
levels: the host leg at CPL3, where **IF is always 1**, and the emulated one at CPL0, where the
prologue's `pushfq/popfq` leaves **IF 0**. So every family-2 case differed by exactly `0x200` in
the stored word — and in the stack copy `pushfq` leaves behind.

The document's contract for flags is run.js's `MASK_ARITH` (`CF|PF|AF|ZF|SF|OF`), which is what the
dedicated flags element compares; the case's *memory* stores carried bits that element deliberately
excludes. **Fixed in the generator**: every flags store is followed by `and dword ptr [slot], 0x8D5`
and `and dword ptr [rsp - 8], 0x8D5` (the stack copy). Those two lines are 32-bit encodings
(`0x81 /4`), i.e. an **existing** body reached through the mode-aware resolver, so the fix needed no
new instruction semantics — and they are the reason the corpus was regenerated (57 images, the
flags-bearing ones changed by four bytes each).

**The alternative was rejected on evidence**: making the emulated machine's IF match the host's
(`push 0x200 / popfq` in the prologue) would align the artifact without touching the corpus, but it
leaves the emulated guest with interrupts ENABLED in every corpus image, where a device interrupt
would be delivered mid-body — the corpus's determinism would then depend on the device state. The
mask is the honest fix: it compares the bits the contract owns.

## 6. What this slice does NOT cover, named rather than implied

- **`0x81` (the imm32 ALU group) and the accumulator-immediate forms** `0x05/0x0D/0x15/0x1D/0x25/
  0x2D/0x35/0x3D` have **no entry in the overlay at all**, so with `REX.W` they stop by name
  (`0x81 has no 64-bit form …`). They are not landed because **no corpus case exercises them**, and
  this tree does not land an encoding with no instrument. They are the obvious next addition to
  family 2 (sixteen more bodies, both operand orders) whenever a case exists to grade them.
- **`0xF7`'s `/0` and `/1` (`test r/m64, imm32`)** likewise stop by name (S8's group-mate).
- **`mul/imul/div/idiv`** are S8's; `alu-div-zero` is RED for that reason and the gate asserts the
  reason (`instr64_F7_6`), not just the count.
- **AF on a LOGIC operation is not verified**, deliberately: the SDM leaves it undefined there, and
  the corpus may not contain an undefined-case (plan §2.1.5's "out of reach by rule").
- **A faulting store's flag behaviour** diverges from the reference in a way no run here can see
  (§4's note in `instructions_64.c`): the reference pre-translates the write address, so a faulting
  store leaves the flags untouched; these bodies compute (and therefore set) the flags first. A
  `#PF` handler that reads the flags mid-instruction would see the difference; no corpus case can
  build one.
- **The `0x8F /1../7` sub-ops** (the invalid LDS/`xrstor` slots) remain `#UD`/stops as before.
