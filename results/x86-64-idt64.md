# x86-64: the amd64 guest's first 626,000 instructions — six MEASURED defects, and the IDT64 unit's honest scope

**Status: landed, gates green, guest STILL BLOCKED (a different gap).** This unit was briefed as
"close the named gap blocking the amd64 guest — the 64-bit IDT gate decode and interrupt frame".
The IDT gate decode was **not** the blocker: the guest never reached a legitimate interrupt. What
blocked it was a chain of six defects, five of them outside the brief, and closing them moved the
pinned guest kernel from **30,594** instructions to **626,389** (a 20× reach) — into the
decompressor's C code. It stops there on a seventh gap (`rep movsb` raising a #GP the hardware
would not), which is recorded at §6 and is *not* closed.

Every claim below is tagged: **MEASURED** (this tree, this run), **READ** (a source file I read),
**INTERPRETATION**, or **PROJECTION**.

## 2. The six defects, each with the evidence that found it

### 2.1 A null SS selector IS legal in 64-bit mode at CPL 0 (MEASURED defect, READ source)

The stop at the unit's start was:

    call_interrupt_vector: invalid gate type 0 for vector 13 (idtr base 0x8d1280 limit 255,
    descriptor at 0x8d12e8 = 0x0, faulting rip 0x100208 …)

A null IDT (limit 255, every descriptor 0) means *any* fault is fatal, so the question was which
fault the port invented. A temporary probe in `switch_seg` (removed; §7) gave:

    PROBE switch_seg(SS) sel=0x0 cpl=0 gdtr base=0x8d1010 limit=0x2f lookup=1 … efer=0x500

`lookup=1` is `SELECTOR_LOOKUP_IS_NULL`, and the port's protected-mode rule answered it with
`trigger_gp(0)`. The instruction is `8e d0` (`mov ss, ax`) at guest `0x100208`, with `AX = 0`.

**Is that legal?** The kernel says yes (READ, linux v6.1
`arch/x86/boot/compressed/head_64.S:334-356`):

    	.code64
    	.org 0x200
    SYM_CODE_START(startup_64)
    	cld
    	cli
    	/* Setup data segments. */
    	xorl	%eax, %eax
    	movl	%eax, %ds
    	movl	%eax, %es
    	movl	%eax, %ss
    	movl	%eax, %fs
    	movl	%eax, %gs

The 0x200 entry is the ABI-immutable 64-bit entry point and it runs on hardware, so the
protected-mode null-selector rule cannot apply to SS in 64-bit mode at CPL 0. QEMU encodes
exactly that exception (READ, `target/i386/tcg/seg_helper.c:1293-1302`, v8.2.0):

    if ((selector & 0xfffc) == 0) {          /* null selector case */
        if (seg_reg == R_SS
    #ifdef TARGET_X86_64
            && (!(env->hflags & HF_CS64_MASK) || cpl == 3)
    #endif
            ) { raise_exception_err_ra(env, EXCP0D_GPF, 0, GETPC()); }

Note the **CPL-3 half**: at CPL 3 in 64-bit mode a null SS *is* a #GP. The port now implements
QEMU's condition verbatim (`src/cpu/exceptions.c`, `switch_seg`'s IS_NULL arm), and clears
`segment_offsets[reg]` for the 64-bit-mode null load of SS/DS/ES (CS/DS/ES/SS bases are
architecturally 0 and `modrm_resolve64` adds the field unconditionally), while **not** clearing
FS/GS (their base is the MSR's, `cpu_state.h:428`).

`v86/` cannot arbitrate this: it has no long mode and its `switch_seg` is the 32-bit rule.

### 2.2 `0x81` — the imm32 ALU group — had no 64-bit body (MEASURED defect)

Next stop: `long mode: 0x81 has no 64-bit form in gen/x86_table64.js` at `0x100228`, whose bytes
are `48 81 fd 00 00 00 01` = `cmp rbp, 0x1000000`. S6's overlay note listed 0x81 as a **named
stop** ("no corpus case covers it"), which is the right rule — so the encoding arrived with an
instrument, not alone: 16 bodies (`instr64_81_{0..7}_{mem,reg}`, imm32 sign-extended by
`read_imm32s`) plus the corpus case `alu/imm32-group-64` (all eight sub-ops, register and memory
form, and the sign-extension discriminator `sub r10, 0xFFFFFFFF80000000`).

### 2.3 `0xCB` — 64-bit `retf` — had no body (MEASURED defect)

`0x100266` is the decompressor's trampoline (READ, `head_64.S:440-446`):

    	/* Reload CS so IRET returns to a CS actually in the GDT */
    	pushq	$__KERNEL_CS
    	leaq	.Lon_kernel_cs(%rip), %rax
    	pushq	%rax
    	lretq

The port stopped on `instructions::instr64_CB`. `instr64_CB` now reads the **16-byte** frame
(8-byte RIP + 8-byte CS slot, upper 48 discarded) and calls `far_return` with `stack_adjust = 8`
(the difference from the 32-bit frame it assumes) and `is_osize_32 = true`. Two **named stops**
rather than silent truncation, both consequences of `far_return`'s `int32_t eip`: a target at or
above 4 GiB, and a RETF that changes privilege level (that path reads a 32-bit ESP/SS frame).

### 2.4 The LEA sentinel aborted the host (MEASURED defect, host SIGABRT)

Next came a *host* abort, not a guest stop:

    ./src/cpu/modrm.c:38: assert(prefix != 7) failed
    cosmoaddr2line: modrm_resolve64 -> modrm_resolve -> instr32_8D_mem -> long_mode_rex_prefix

`instr16_8D_mem`/`instr32_8D_mem` set `SEG_PREFIX_ZERO` (7) in the segment field so the *32-bit*
resolver adds no base (LEA computes an address and reads no memory); `get_seg_prefix` maps 7 to 0.
`segment_prefix` **asserts** instead — and `modrm_resolve64`, written in S5a, called it
unconditionally. The 64-bit resolver now handles the sentinel before calling `segment_prefix`.

### 2.5 A 32-bit LEA above 4 GiB is the instruction's own semantics (MEASURED defect)

With 2.4 fixed the same LEA hit S5a's address bound:

    modrm: a 64-bit effective address above 4 GiB in a 32-bit-operand form

A probe printed the registers at the stop: `modrm=0x14 prefixes=0x1507 a=0x100000000 rip=0x8bd1b6`,
`r9=0x00000000fff72000`, `rdi=0x000000000008e000`. The instruction is `45 8d 14 39` =
`lea r10d, [r9 + rdi]`, and `0xFFF72000 + 0x8E000` is **exactly 0x1_00000000**. A 32-bit LEA stores
the LOW 32 BITS of the effective address — truncation *is* the instruction. The bound's purpose is
the silent-wrap class (a *memory* address truncated by a 32-bit body), so it now exempts the LEA
sentinel and keeps every other encoding stopped by name.

### 2.6 `0F 47` — the cmovcc family — had two of sixteen bodies (MEASURED defect)

`long mode: 0F 47 has no 64-bit arm` at `0x4F3F178` (the decompressor, now relocated to
`0x4F30000`+). 0F 44/45 existed (the corpus's `ctrl-cmov`); the other fourteen conditions were
named stops. All sixteen are now bodies over the port's **own** `test_*` predicates
(`misc_instr.h`), with `ctrl/cmov-family` as the instrument: one flag state
(`cmp rax, rbx` with `rax=0x100000000`, `rbx=0xFFFFFFFF` → OF=CF=ZF=SF=PF=0) makes the eight even
conditions all move and the eight odd ones all leave their destination at zero, so a swapped
predicate pair changes half the window.

### 2.7 REX.B was dropped on opcode-implied registers — `mov r12d,1` became `mov esp,1` (MEASURED defect)

The #PF that followed had `cr2 = 0xfffffff9` (`-7`) and a trace probe showed `rsp = 1`:

    PROBE #PF addr=0xfffffffffffffff9 write=1 rip=0x4f3f1fb rsp=0x1
    PROBE   rip=0x4f3f124 op=0x48 rsp=0x4f56f90 after=0x4f3f12b bytes 48 23 05 a5 22 01 00 41 bc 01 00 00 00
    PROBE   rip=0x4f3f131 op=0x49 rsp=0x1      after=0x4f3f135

The bytes at `0x4f3f12b` are `41 bc 01 00 00 00` = `mov r12d, 1`. `REX.B` with no `REX.W` selects
the **32-bit** arm, and the port's 16/32-bit `+r` bodies hardcoded the register
(`instr32_BC(int32_t imm) { write_reg32(ESP, imm); }`) — so the guest's stack pointer became 1 and
its next `call` pushed to `0xFFFFFFFFFFFFFFF9`.

**The class, not the instance:** the destination of an opcode-implied register is `opcode & 7`
extended by REX.B, and REX.B is live whenever a REX byte is present, including the REX byte of a
32-bit-operand form. 38 bodies were rewritten to `reg_index_b(n)`: `instr_B0..B7` (mov r8, imm8),
`instr16/32_B8..BF` (mov r, imm), `instr16/32_91..97` (xchg r, eax). `0x50-0x5F` need nothing —
their 16/32-bit arms are unreachable in 64-bit mode (the overlay's `default64` entries route them
to the 64-bit bodies and the 16-bit forms stop by name). Outside long mode `reg_index_b` is the
identity, so the 32-bit machine is untouched (§4's pins are the proof). Instrument:
`ctrl/rexb-implied-register`.

### 2.8 The accumulator-immediate forms had no 64-bit bodies (MEASURED defect)

`long mode: 0x25 has no 64-bit form` — `48 25 …` is `and rax, imm32` with the immediate
sign-extended. Eight bodies (`instr64_05/0D/15/1D/25/2D/35/3D`, `int64_t imm` from
`read_imm32s`) with `alu/accumulator-imm32` as the instrument.

### 2.9 `FF /2` — indirect near `call` — had no 64-bit body (MEASURED defect)

`instructions::instr64_FF_2_mem`. `/4 jmp r/m64` and `/6 push r/m` were already S7's; `/2` was
still a named stop. `instr64_FF_2_{mem,reg}` read the target FIRST (so a faulting
`call qword [mem]` leaves rsp untouched and re-executes cleanly), then push the next instruction's
address, then transfer. Instrument: `ctrl/indirect-transfer`. `/3 callf` and `/5 jmpf` remain
named stops.

### 2.10 Two instrument defects found in this unit's own evidence path

* **The stop message was CUT MID-EVIDENCE.** `unimplemented_name` was `char[160]`
  (`src/cpu/cpu.c:65`) and the gate-type stop carries the IDT base/limit, the descriptor, six
  bytes at rip and now cr2/cr3: the reported bytes ended at `… 8e d0 8e e0 8` (MEASURED, the stop
  string in §2.1's first run). Buffer is 384 now, and the message additionally carries `cpl`,
  `cr2` and `cr3` — `cr2` is what identified §2.7.
* **`exceptions.c` used `snprintf` with no `<stdio.h>`.** The unity build hid it (main.c includes
  stdio); `make selftest`'s standalone compile of `exceptions.c` did not:
  `implicit declaration of function 'snprintf'` → `-Werror`. Fixed at the include.

## 3. The IDT gate decode and the interrupt frame: what this unit did and did NOT validate

* **LGDT/LIDT's 10-byte long-mode operand** (landed earlier in this unit, `instructions_0f.c`):
  MEASURED necessary — the decompressor's `lgdt gdt64(%rip)` (`head_64.S:437-439`) loads a
  2-byte limit + **8-byte** base, and a 6-byte read leaves the GDT base truncated. After the fix
  the guest's GDT is read at its real base (`gdtr base=0x8d1010 limit=0x2f` in §2.1's probe, and
  `0x4f51050`-relative addresses later).
* **The gate-type stop's evidence** (landed earlier in this unit): kept and extended (§2.10).
* **THE 64-BIT INTERRUPT FRAME IS *NOT* VALIDATED.** The frame push in `call_interrupt_vector` is
  still 32-bit, and **no deliverable interrupt has been reached**: every stop in §1 is a fault
  whose IDT entry is null (the decompressor's stage-1 IDT, limit 511, has no #GP/#PF gate), so
  hardware would triple-fault there too. The `gate-x86-64.sh` step named
  `stop-is-the-64bit-interrupt-frame` asserts the *stop*, not a delivered frame. **This is the
  unit's headline gap and it is unchanged**: the frame work cannot be validated until a guest
  reaches an interrupt with a real gate.

## 7. Instrument discipline (what was temporary, and that it is gone)

Three probes were added and **removed** before the gates were run: a `switch_seg(SS)` dump in
`exceptions.c` (§2.1), a `modrm_resolve64` register dump (§2.5), and a
`trigger_pagefault` + `interpreted_run` ring buffer of `(rip, opcode, rsp, rip_after)` (§2.7 —
this is what turned "the guest is somewhere odd" into `mov r12d,1` → `mov esp,1`).
`rg TEMP-PROBE src/` returns nothing. Two probes became **permanent evidence** because they are
stop messages, not instrumentation: the gate-type stop's buffer size and `cr2`/`cr3` fields
(§2.10).

**One probe design error, recorded so it is not repeated:** the trace printer stepped its window
by two (`k -= 2`), so every second entry was hidden and one instruction appeared to have consumed
13 bytes when it had consumed 7 — a whole round of the §2.7 investigation was spent on an
instrument artefact. *A trace that samples is not a trace.*
