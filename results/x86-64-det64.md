# x86-64: the two configurations are each self-reproducible — the divergence is the guest's own KASLR

**Status: MEASUREMENT ONLY (four boots, two per configuration; no source change). The port is
deterministic in BOTH configurations: each run of a configuration reproduces its instruction count and
its serial BYTE FOR BYTE. The divergence is therefore between configurations, and its cause is visible in
the serial itself.** Claims tagged MEASURED / READ / INTERPRETATION.

## 1. Self-reproducibility, both configurations (MEASURED, back-to-back pairs)

| configuration | run 1 | run 2 | serials |
|---|---|---|---|
| KASLR (default cmdline) | `4590876590` instr, `eip=0x897e42c6`, rc 1 | `4590876590` instr, `eip=0x897e42c6`, rc 1 | **byte-identical** |
| `nokaslr` | `6000004874` instr (the 6 G budget), `unimplemented=0`, rc 0 | `6000004874` instr, rc 0 | **byte-identical** |

`cmp` on each pair: identical. So **no host-side nondeterminism is proven** — and the two determinism
runs the brief asks for are exactly these four boots (each configuration is its own control).

## 2. The host-clock suspicion, checked and cleared (READ + MEASURED)

`grep` over `src/cpu/*.c`/`*.h` for `clock_gettime|gettimeofday|time(NULL)|rdtsc`: the only hits are
comments — `cpu.c:409-410` states that the REFERENCE's `rdtsc` reads a wall clock and that no fixture
which executes it may be compared for its TSC value, and `cpu_state.c:311` records that this port has no
host-clock TSC. **The measurement backs that up: a host clock would make two runs of the same
configuration differ, and they do not** — the same 4,590,876,590 and 6,000,004,874 instructions twice,
with identical serials.

## 3. What actually differs between the two configurations (MEASURED, from the serials)

    KASLR run:    Invalid physical address chosen!
                  Physical KASLR disabled: no suitable memory region!
    nokaslr run:  KASLR disabled: 'nokaslr' on cmdline.

The decompressor's own physical-placement attempt **fails on this port** ("Invalid physical address
chosen!") and falls back, which leaves a different memory layout and a different virtual slide; `nokaslr`
skips the attempt entirely. The two configurations therefore execute **different kernel code paths**, and
the KASLR one ends in the fault-delivery stop (`a fault raised while delivering a fault`, once) while the
`nokaslr` one is still making progress (`unimplemented=0`) when the 6 G budget runs out.

**INTERPRETATION: this is the guest's own KASLR doing its job, not a determinism defect.** Same binary,
same settings, same result every time; different settings, different guest code path.

## 4. The instrument note for the gate (no code change)

`tests/gate-x86-64.sh`'s `stop-is-the-next-unimplemented-body` step asserts
`grep -q 'a fault raised while delivering a fault' $BOOTLOG` — a **message**, not an address, which is the
right shape — but that message is produced only by the KASLR configuration: the `nokaslr` run does not
produce it at all (0 occurrences). So the step is valid for the gate's own configuration and would fail
under `nokaslr`. The KASLR-independent property both configurations share is the **console**: the banner,
`percpu: Embedded …`, and `Spectre V1 : Mitigation: …` are in both serials. **Recorded, not changed** —
the gate passes today (14/0) and rewriting its step is a decision for a unit that owns the gate, not a
side effect of a measurement.

## The ONE next measurement

**Symbolicate the KASLR configuration's stop `eip=0x897e42c6`** — it is reproducible, so the slide can be
recovered from the same run (the port's dump prints `cr3`/`gs_base`; the kernel's own virtual slide is the
one unknown) and the instruction read at the break. That is now the only unknown left in the pair: the
`nokaslr` configuration is the CONTROL — it does not stop at all — so a defect found in the KASLR path is
either a real kernel path the port breaks or a consequence of the decompressor's failed physical-KASLR
placement ("Invalid physical address chosen!"), and the next measurement must say which.
