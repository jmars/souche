# x86-64: the rep string family at long mode's widths, and the 64-bit IDT gate it uncovered

**Status: both parts landed; the guest now decompresses (30.2 M instructions, its own console
alive) and stops on a 64-bit address the 32-bit-arm bodies cannot carry. One claim from
`results/x86-64-idt64.md` is REFUTED by measurement here and is corrected in §3.**

Part (A) was the brief's subject: `f3 a6` was reported as `rep movsb` raising a #GP. It is
**`repe cmpsb`** (0xA6 is CMPS; 0xA4 is MOVS), and the #GP had a cause that had nothing to do with
the string code (§1). Part (B) asked whether the kernel's stage-1 IDT is really all-null; it is
**not** (§3), and the reason the port reported otherwise was an 8-byte descriptor stride over
16-byte gates (§4) — the original "64-bit IDT gate decode" gap, finally measured.

Every claim is tagged **MEASURED** / **READ** / **INTERPRETATION** / **PROJECTION**.

---

## 1. The #GP was `get_seg`'s null-segment check, not the string code (MEASURED)

The stop was

    invalid gate type 0 for vector 13 … faulting rip 0x4f3cd4d bytes f3 a6 74 37 48 83, cpl 0 cr2 0x0

`f3 a6` = `repe cmpsb`, which reaches `string_instruction` with `STR_CMPS`. CMPS reads **both**
operands, so it calls `get_seg(ES)` — and ES had been loaded with a **null selector** by the
kernel's own entry point (§2.1 of the previous report). `get_seg` (modrm.c:84) answered a null
segment with `trigger_gp(0)`, into a stage-1 IDT with no #GP gate.

**In 64-bit mode the null flag is not checked at all**: DS/ES/SS are loaded with null selectors as
a matter of course, their bases are architecturally 0, and a memory access through them performs no
segment-validity check. The arm is now gated on `!long_mode_64()`. **MEASURED**: the same run went
from `eip=0x4f3cd4d` (626,389 instructions) to `eip=0x4f3c34f` (629,085).

## 2. Part (A): the string family at 64-bit widths

### 2.1 What was wrong

`string_instruction` (string.c) is 32-bit end to end: `read_reg32(ECX)` for the count,
`read_reg32(ESI/EDI)` for the pointers, `int32_t` addresses, and `set_reg_asize` (which writes a
16-bit register when the address size is not 32). S9's `str64_*` bodies in instructions_64.c did
the Q (8-byte) forms correctly and nothing else did. So in long mode `repe cmpsb` truncated
RSI/RDI/RCX to 32 bits and could not address above 4 GiB.

### 2.2 What landed

* `string.c` gains a **64-bit path** (`string_instruction64`), entered at the top of
  `string_instruction` when `long_mode_64()`. The 32-bit path below it is untouched — that is the
  M0 transcript's guarantee, and §5's pins are the proof.
* The 64-bit path gets, by construction and by test: **RCX/RSI/RDI at 64 bits**; **0x67** narrows
  them to 32 with the architecture's **zero-extending write-back**; **DF** selects the direction
  and the step is the **operand width**; `STR_Q` makes REX.W's 8-byte forms (`MOVSQ`/`CMPSQ`/
  `STOSQ`/`LODSQ`/`SCASQ`) real through the same code; **repe/repne exit on ZF** after the
  comparison that set it; and a **fault keeps the partial effects** (the pointers reflect the
  iterations that completed, and RCX still counts the faulting one, because the instruction is
  re-executed after `iret`).
* The five hand-written `str64_*` loops in `instructions_64.c` were **replaced** by calls into the
  shared path (15 one-line entry points). A second copy of the semantics is a second thing to keep
  right; the corpus shows the shared path is judged at all five widths.
* `paging.c`/`paging.h` gain the four accessors the header said would "arrive with S7" and did not:
  `safe_read16_addr`/`safe_read32_addr`/`safe_write16_addr`/`safe_write32_addr`, each with the
  32-bit twins' page-straddle split. The string path needs every width at a 64-bit linear address.

**NAMED GAP, not reworded:** the 64-bit path has **no fast path** (no bulk `memcpy`/`memset` for a
whole page). It runs one iteration per loop pass through the safe accessors, which is the SLOW
path's semantics exactly; the fast path is an optimisation whose absence costs speed, never
correctness, and **no instrument can distinguish the two paths** because they must agree — so it is
recorded rather than faked.

### 2.3 The instruments (MEASURED, and one of them caught my own bug)

New corpus family `str` (S9b), four cases, all green against the host on all three engines:

| case | what it proves |
|---|---|
| `str/cmps-count-64` | **the counter is RCX, 64 bits.** `repe cmpsb` with RCX = 0x100000002 exits on the first mismatch and must leave RCX = **0x100000001**; a 32-bit counter reads ECX = 2, exits identically, and writes back **1**. The ZF exit is the only way to observe the counter's width without a 2^32-iteration run. |
| `str/scas-count-64` | the same for the `repne` exit: RCX = 0x100000003, first byte matches, RCX must be **0x100000002** and ZF = 1. |
| `str/asize-67` | the **0x67** override: with the high halves of RSI/RDI set, `addr32 rep movsq` must read/write at 0x100140/0x100150 (a 64-bit address size would fault) and leave RSI = **0x100148**, not 0x100000100148. |
| `str/df-64` | **DF = 1** walks the 64-bit pointers DOWNWARD (a body that always increments copies the wrong bytes). |

Plus `ctrl/cdqe-cqo-64` (§6). The corpus also carries S9's `strobits-*` cases for the Q opcodes.

**The instrument caught a bug in the new code (MEASURED):** the first draft keyed the ES:(E)DI side
off the *store* instead of the *operand*, so `repe cmpsb` compared against address 0 and did not
advance RDI — `str-cmps-count-64` reported `reg64[7] (rdi) actual 0x100120, expected 0x100121`. The
two questions are now separate named predicates (`uses_esi`/`uses_edi`).

**Residual gap, stated:** for `rep movs/stos/lods` (no ZF exit) a counter above 2^32 cannot be
instrumented without a 4-billion-iteration run, so the counter's width is proven only for the
comparing forms; the other three share the same `string64_set_reg(asize_32, ECX, count)` call site.

## 3. Part (B): the stage-1 IDT is NOT all-null — the previous report's claim is REFUTED (MEASURED)

`results/x86-64-idt64.md` §3 said every stop was "a fault whose decompressor stage-1 IDT entry is
null … where hardware triple-faults too". **That is wrong for #PF**, and the measurement that
refutes it is a dump of the guest's IDT at the stop (idtr base `0x4f51050`, limit `511` = 32
16-byte gates), decoding each slot at the 16-byte stride:

    idt[ 2]  c0 f8 10 00 00 8f f3 04 00 00 00 00 00 00 00 00   -> handler 0x4f3f8c0, sel 0x0010, type 0x8F (P=1 DPL=0 trap)
    idt[14]  70 f8 10 00 00 8f f3 04 00 00 00 00 00 00 00 00   -> handler 0x4f3f870, sel 0x0010, type 0x8F
    idt[ 0,1,6,7,13,18,…]  all zero

So **vector 14 (#PF) has a real, present, DPL-0 trap gate** (`boot_page_fault`), and so does vector
2 (NMI); everything else is null. READ (`arch/x86/boot/compressed/idt_64.c`, v6.1): `load_stage2_idt`
installs exactly `X86_TRAP_PF` (and #VC under `CONFIG_AMD_MEM_ENCRYPT`), which matches the measured
vector 14 gate.

**What that means:** the previous report's stop was a **#PF whose gate existed** and which the port
refused to deliver — because of the stride bug in §4. The 64-bit interrupt frame was reachable all
along. What the guest could prove at that stop, and now does prove (§4.2), is the delivery itself.

## 4. The 64-bit IDT gate and the 8-byte frame (landed, and PROVEN by a selftest arm)

### 4.1 The three defects

1. **The stride.** `call_interrupt_vector` computed `idtr_offset + (vector << 3)` — the 32-bit
   gate's size. A 64-bit gate is **16 bytes** (MEASURED: `idt[14]` lives at base + 0xE0, and the
   port read base + 0x70 = vector 7's null slot, which is why a real #PF was reported as "invalid
   gate type 0"). The stride is now `vector * gate_size` with `gate_size = 16` in long mode.
2. **The offset's high half.** `intr_descriptor_offset` composes offset_low | offset_middle << 16
   from the first qword; a 64-bit handler address also has offset_high in bytes 8-11. Long mode now
   reads the second qword and composes `offset64`.
3. **The frame.** `intr_descriptor_is_32` is TRUE for a 64-bit gate (types 0xE/0xF carry bit 3), so
   the old code took the 4-byte push path. Long mode now pushes **RFLAGS, CS, RIP (and the error
   code) as eight bytes each** — the 40-byte frame, of which the intra-privilege case pushes four
   qwords (no SS/RSP).

**NAMED STOP:** a **CPL-changing** interrupt delivery in long mode (the 8-byte SS/RSP pair from the
TSS and the IST stack) is not implemented and stops by name. The decompressor's faults all arrive
at CPL 0 on the same stack.

### 4.2 The instrument that proves it (MEASURED, with its able-to-fail arm)

`m1c_selftest.c` gains **TEST 1b** — a #PF delivered through a real 16-byte gate in 4-level paging:

* the IDT has a gate at **vector 14 only**, written at the 16-byte stride, with handler
  **0x123458000** (a high half, so a 32-bit decode delivers to 0x23458000);
* the gate's CS (0x18) is a **64-bit** code segment (L=1, D=0), so the delivery must leave long mode
  ON;
* the frame is read back at 8-byte offsets: `[rsp]` = #PF error code (0), `[rsp+8]` = the **rewound**
  rip (0x7000), `[rsp+16]` = the interrupted CS (0x08), `[rsp+24]` = RFLAGS, and RSP =
  STACK_TOP - **32**.

**THE ABLE-TO-FAIL ARM IS MEASURED, not asserted:** reverting the stride to `vector << 3` makes the
test fail on four checks —

    FAIL cpu->instruction_pointer == HANDLER64 (got 0x7000, want 0x123458000)
    FAIL cpu->sreg[CS] == SEL_CODE2      (got 0x8,    want 0x18)
    FAIL read_reg64(ESP) == STACK_TOP-32 (got 0x7000, want 0x6fe0)
    FAIL safe_read64_addr(frame + 8) == 0x7000 (got 0x0)

and the fix makes it pass (`cpu_m1c_selftest` 258 → **272** checks). This is the step
`tests/gate-x86-64.sh` could only assert the *stop* of.

### 4.3 What the GUEST proves, and what it does not

The guest **never reaches a fault now**: after the fixes it decompresses past 30 M instructions and
stops on a **64-bit effective address above 4 GiB** (§6). So the delivered frame is proven by the
selftest arm, **not by the guest** — stated because the previous unit was criticised (correctly) for
asserting a stop instead of a frame.

## 6. The guest's state now, and the next named gaps (with evidence)

    v86c boot: 30184930 instructions, in_hlt=0, exception=-1, unimplemented=1,
               eip=0x4f3a7e8 cs=0x10 cr0=0x80050033 cr3=0x4f76000
    v86c: unimplemented: modrm: a 64-bit effective address above 4 GiB in a 32-bit-operand form

Serial: `Physical KASLR disabled: no suitable memory region!` — the decompressor's own console.

Probe at the stop (MEASURED): `modrm=0x44 prefixes=0x0000 a=0x12cd38220 rip=0x4f3a7e8`, with
`r9 = 0x9669c110`; `0x9669c110 << 1 = 0x12cd38220` exactly, so the address is a legitimate 64-bit
effective address (a scaled 64-bit index) and not a miscomputation. The port's 32-bit-arm bodies
take an `int32_t` address, so this is the **S6-S10 "widen the bodies"** gap, now the binding one.

Closed on the way (both were named stops that the guest reached):

* **0x98/0x99 with REX.W = CDQE/CQO** (`instr64_98`/`instr64_99`, overlay entries, corpus
  `ctrl/cdqe-cqo-64`). The 32-bit CWDE arm writes AX only, so the upper half of RAX would stay.
* **`0F C7 /6` with REX.W = RDRAND r64** (`instr64_0FC7_6_reg`, two draws of the port's existing
  deterministic generator, LOW FIRST — upstream has no 64-bit draw, so the composition is the
  port's and is declared). The memory form is `#UD`, as the 32-bit arm and the reference's table
  say (`mem_ud: 1`). **This is what let the guest reach its decompressor**: the KASLR code executes
  `rdrand rax`.

Next, in order: (1) **widen the 32-bit-arm bodies to 64-bit addresses** (the current stop; the
`modrm_resolve` bound is where it lands); (2) the CPL-changing 64-bit delivery and the IST stack
(§4.1's named stop); (3) the long-mode string **fast path** (§2.2's named gap); (4) the remaining
named stops this unit did not touch (`/3 callf`, `/5 jmpf`, the register-source `BT` form,
`far_return`'s 32-bit eip).
