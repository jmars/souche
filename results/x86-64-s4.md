## 2. What landed, piece by piece

### 2.1 The image: the harness is the loader (plan §2.1.1, discharged)

Every corpus case is one `.asm` file carrying a complete image source in three sections
(`tests/nasm64.ld` fixes the addresses):

```
.stub  @0x80000  the 32-bit machine setup: the multiboot ADDRESS TABLE, PML4/PDPT/PD/4xPT
                 identity-mapping the first 4 MiB with 4 KiB pages, a GDT whose 0x08 is a
                 64-bit code segment, CR4.PAE, EFER.LME, CR0.PG, `jmp far 0x08:body_start`.
.body  @0x90000  .code64: the shared prologue (16 GPRs zeroed, rsp = 0x102000, flags clear),
                 the case, the sixteen GPR stores into the window, `loop: hlt; jmp loop`.
.bss   @0x100000 NOLOAD: the compared 8 KiB window, whose top is the stack.
```

**The native leg never executes the stub** (4 KiB-page tables, CR4.PAE, EFER.LME, CR0.PG, a far
jump): it `mmap`s the flat image at 0x80000 with `MAP_FIXED_NOREPLACE`, copies the bytes, maps the
`.bss`/stack region as anonymous zero pages, zeroes the GPRs and the FPU state, and jumps straight to
`body_start`.  **The emulated leg never needs a new loader**: the port takes the multiboot
address-table branch it already has (`src/main.c:284-341`) and enters the stub.  That is the plan's
argument, unchanged — the new code lives in a test rig, not in the shipped `load_elf`.

MEASURED consequences of that choice, each of which is a limitation worth stating:

* the flat image must END before 0xA0000, because the port's loader refuses a blob that overlaps the
  memory-mapped hole (`in_mapped_range`, `src/main.c:232-236`).  Hence `.bss` is NOLOAD and a fresh
  image is ~64 KiB (`.stub` + the 0x10000 gap + `.body`, MEASURED 65,745-65,816 bytes across the
  corpus).  A case that needs more body space than the gap allows is a case that fails to link, not
  a silent truncation.
* the native leg maps exactly `[0x80000, 0x103000)` (`MAP_END`, one page past the stack top), so a
  case cannot address outside it; the identity map stops at 4 MiB for the same reason (S5's bound).
* **the stub is executed by NEITHER leg in this slice**: the native leg skips it by design, and the
  emulated leg stops inside it at `unimplemented: EFER.LME asks for IA-32e …`.  Its own success is
  therefore asserted by nothing yet.  From S5 every case asserts it at once (a body cannot run
  otherwise), which is the plan's own formulation.

### 2.2 The document: format v2, one printer, two consumers

`tests/mkfixture64.c` emits the v2 array, 2124 elements (MEASURED on all 57 cases):

```
[ 0..15]  the 16 GPRs, signed decimal of the 64-bit value, in cpu_state.h's reg64[] order
[16]      rip
[17.. 24] st0..st7 (a float, or "invalid")
[25.. 40] mm0..mm7, two 32-bit words each (the low 64 bits of PHYSICAL st(i))
[41.. 72] xmm0..xmm7, four 32-bit words each
[73..2120] the 8 KiB window at 0x100000, 32-bit words, signed
[2121]    rflags          [2122] the x87 tag word        [2123] the x87 status word
```

`--fixture64` prints **the same array from the port**, and then a `---BEGIN STATE---` control tail
(`efer`, `cr0-cr4`, `gdtr`/`idtr`, the six segments' selector/base/limit, the `sysenter` triple,
`state_flags`, `ip`, `previous_ip`, `instruction_count`, and the MODE).  The corpus comparator
ignores the tail; the plan's two consumers read it (§5.4): the 64-bit engine differential (S13) and
the KVM lane's state translation.

**The two documents are ONE printer** (`print_fixture(bool wide)`, `src/main.c:671`): the 32-bit
branch prints exactly the expressions it always did, so the M0 transcript's bytes cannot move.  The
gate proves that structurally rather than by assertion — §4's step A runs one image both ways and
requires 2116/2124 elements, the same eight registers (low halves and signs), R8-R15 zero, the same
rip, and an identical x87/MMX/XMM/memory/flags block (MEASURED 6/6 clauses).  **Without that step the
v2 printer would be a seat nobody sits in until S5.**

Two conventions the two producers must agree on, both stated in the code so they are not guessed:

* **signed decimal of the 64-bit value** in the wide register block (both producers), which is why a
  32-bit-mode register prints positive here and negative in the narrow document: the wide document
  prints the field, the narrow one prints `(int32_t)(uint32_t)` of it (S1's re-pin).
* **R8-R15 DO NOT EXIST IN THE MODEL YET** (plan §4's inventory: `reg64[8]` is eight slots).  The
  wide block's elements 8-15 are the seat, and their honest current value is ZERO.  A case that USES
  r8-r15 therefore cannot agree until S5 — one of the mechanical ways a family stays RED.

### 2.3 The corpus: generated from a declaration, with a witness rule

57 cases over the six families the later slices own (MEASURED, `gen/nasm64_gen.py --list`):

| family | slice | cases | what it covers |
|---|---|---|---|
| `mov` | S5 | 12 | `MOV r64,imm64`, imm32 sign-extend, 32-bit zero-extend, REX.B/REX.R (r8-r15), `spl/bpl/sil/dil` vs `ah/bh/ch/dh`, 8-byte memory immediates, RIP-relative, SIB with a 64-bit base+index, the `0x67` address-size override, `A1/A3` moffs64 |
| `alu` | S6 | 10 | add/adc/sub/sbb/and/or/xor/test/cmp/inc/dec/neg/not at 64 bits, the 32↔64 sign and carry boundaries, an `#DE` case |
| `ctrl` | S7 | 12 | jcc, call/ret, push/pop (64-bit, `push imm`), lea, movsxd, movzx/movsx, cmov, setcc, xchg, an indirect jump, `#UD` |
| `muldiv` | S8 | 11 | mul/imul (128-bit results), div/idiv, shl/shr/sar, rol/ror, bt/bts/btr/btc, bsf/bsr, bswap, shld/shrd |
| `strobits` | S9 | 6 | `rep stosq`/`movsq`, `scasq`/`cmpsq`, `lodsq`, cmpxchg, xadd, **cmpxchg16b** |
| `simd` | S10 | 6 | movq, movdqa, paddq/pxor, cvtsi2sd, `fild`/`fistp`, MMX through a 64-bit address |

**THE WITNESS RULE (plan §7 R4) IS MECHANICAL, NOT A HOPE — and in its first form it was UNSOUND
(round 2, fix 5; §9.5).**  The rule now tests the property it claims: every case must contain a
construct that **cannot be encoded in 32-bit mode**, in one of three classes, with **values parsed**
rather than spelling-matched:

* **W1 VALUE** — a literal whose VALUE is at or above 2^32, used in an instruction (not in a data
  directive: a `.quad` holds any width).  There is no 64-bit immediate in 32-bit mode.
* **W2 REGISTER** — an REX-only register: `r8`-`r15` in any width, and `spl/bpl/sil/dil`.  In 32-bit
  mode those encodings are `INC`/`DEC` or `AH`/`CH`/`DH`/`BH`.
* **W3 ENCODING** — `MOVSXD` (0x63 is `ARPL` there) or `CMPXCHG16B` (no counterpart).

Explicitly **not** witnesses, each because the instruction exists in 32-bit mode: `MOVZX`/`MOVSX`,
`XADD`, `BSWAP`, `SHLD`/`SHRD`, the bit-test and bit-scan group, `MOVQ`/`MOVDQA`/`PADDQ`/`PXOR`/
`CVTSI2SD`, `FILD`/`FISTP`, the string group, `PUSHFQ`/`POPFQ`, the `qword ptr` and `[rip+...]`
spellings, and a 64-bit spelling of a legacy register with a small value (`mov rax, 5` behaves
exactly like `mov eax, 5`).  The generator **refuses to write a case with no witness**
(`InventoryError`), and it carries its own able-to-fail battery (`--witness-selftest`, 20 verdicts:
the review's three measured false accepts, the zero-padded literal, the decimal at or above 2^32,
and the positive classes) which the gate runs as step B2.

The rule is a **necessary condition, not a proof of discrimination** — it cannot decide that a value
at or above 2^32 *survives* to a compared slot.  The proof of discrimination is the corpus's own
RED-before-green (plan §2.1.7b).  **The two faulting cases are the one admissible exception and are
labelled as such in their own headers**: `#UD` faults at the same rip at both widths, so `ctrl-ud2`
pins the report and claims no discrimination.

It has fired twice on this slice's own authoring (MEASURED, the generator's own message): the first
`ctrl-push-imm` case had no witness, and round 2's corrected rule refused **six** cases
(`mov-rip-relative`, `alu-sign-boundary-32-64`, `ctrl-lea-64`, `ctrl-jmp-indirect`,
`simd-paddq-pxor`, `simd-fild-fistp64`) which were then **strengthened** — each now carries a
regression-proof construct (`r9`/`r10` on a RIP-relative load, a `0x100000000` boundary, `lea r8`,
`jmp r11`, a 64-bit-lane `PADDQ` wrap, an `FILD` operand that does not fit in 32 bits).  Each case's
file records its witness class in a `# WITNESS:` header and the census counts them per family
(W1 x53, W2 x3, W3 x1).

The census the generator prints is the corpus half of plan §2.1.6's discipline; the **port-table**
half ("how many of the dispatch table's encodings have a long-mode arm, and how many of those have a
case") is stated as S5's, because `gen/x86_table64.js` does not exist yet: **0 encodings have an arm,
so every case is RED by construction.**

### 2.4 The runner: the 32-bit comparison, at 64-bit widths

`tests/nasm64_run.py` is a transcription of `tests/nasm_run.py:156-255` (itself upstream's
`run.js:384-510`) onto the v2 layout: the 16 GPRs, `rip`, `st0-7` with the **same
`FPU_TAG_ALL_INVALID` branch**, `mm0-7`, `xmm0-7`, the 2048 window words, `rflags & MASK_ARITH`, and
the exception kind plus the faulting `rip`.  Two deliberate differences, both in the slice's favour
and both named at the code:

* the register file is 16 x u64 and `rip` is 64-bit, so a mismatch above 2^32 is DETECTED (the
  32-bit comparison masks every value to 32 bits, as upstream does).
* the compared flag mask is **not** widened (`MASK_ARITH` is upstream's), because a mask is a claim
  about what the emulator models (plan §2.1.3).

The comparison's own shape is checked by controls rather than trusted (§4 C): with the native leg on
BOTH sides all 57 cases agree (MEASURED 57/57 — a comparison that cannot pass cannot be said to fail
for the right reason), and one perturbed value per fixture makes every comparable case mismatch and
NAME the field.

Two behaviours inherited from upstream that the controls had to respect, discovered while building
them (**MEASURED**):

1. For a **faulting** case the comparison compares the exception kind and the faulting rip ONLY
   (`run.js:497-505`) — registers, memory and flags are not compared.  So the reg/mem controls must
   exclude the two faulting cases (`--exclude`), and the rip control must select them (`--filter`).
   Stated in the gate rather than worked around.
2. A **stray** `int3` in a body, or a body that runs past `loop`, is not a result: `mkfixture64`
   reports it and exits nonzero (MEASURED: the first version of the generator emitted each case's
   data BEFORE the `loop:` label, so three cases fell through into their `.quad` bytes and
   SIGSEGV/SIGILL'd — the harness caught a corpus bug, which is the instrument's first real use).

**Why the red is UNIFORM, and what that does and does not prove.**  Every case enters the stub (32-bit
code the port CAN run: `cli`, `rep stosd`, the table stores, `lgdt`, `mov cr4`) and stops at the first
`WRMSR(EFER)` asking for `LME` — S2's refusal, whose symbol is the same for all 57.  So the census
proves the corpus **cannot** be green today (the mechanism, mechanically, not by claim), and it does
**not** discriminate between cases: per-case discrimination begins with S5, when the stub must
actually succeed and the body must run.  The progression to watch is exactly this line: from S5 the
count falls family by family, and `mismatch` (a case that RAN and disagreed) is the field that says a
slice has a real defect rather than a missing symbol.

**Gate item (a) in the brief's words — "perturb one byte or one register and show the harness reports
it".**  Done three ways, because a comparison can be blind to a whole field: a register (the register
block), a 32-bit word of the compared window (the memory block), and the rip (the exception block, the
only place upstream compares it).  Each control also has its negative result recorded: before the
controls existed, the perturbed-fixture run reported `mismatch=0 error=57` because the fixtures were
never written (MEASURED — the perturb path's first version raised on the `"invalid"` string in the FPU
block), which is exactly the failure mode a control must not be able to hide: it reported FAIL, and it
was right.

**Two of the three perturbations cannot see the faulting cases, by upstream's own rule.**  That is
why C2/C3 carry `--exclude '(div-zero|ud2)'` and C4 carries the complementary `--filter`.  A reader
who takes "every case mismatched" from C2 as "every case is compared" would be wrong: the fault cases
are compared on their exception kind and rip, and the control says so in its own invocation.

## 4. What the instrument taught us, before it could be green

Three of these are corpus bugs the harness caught; one is a measured property of this host's ptrace
that changed a design; one is a real (and instructive) emulator path.

### 4.1 `EFER.LME` is bit 8, not bit 0 — and the wrong value produced the plan's C5 walk

The stub's first version wrote `mov eax, 1` before `WRMSR(0xC0000080)`.  Bit 0 of `IA32_EFER` is
`SCE`; `LME` is bit 8 (0x100).  So the guest asked for **system-call extensions**, never for IA-32e —
and the port, correctly, did not refuse: it ran the whole stub, set `CR4.PAE`, set `CR0.PG` (S2's
`CR0.PG` refusal is conditional on `EFER.LME`, and it was zero), and then took a **3-level PAE walk
over 4-level tables**.  MEASURED outcome: `--fixture64` printed the machine at `rip 0x800b1` with
`cr0=0x80000011 cr4=0x20 efer=0x1` and `(signal SIGBUS)`, i.e. the walk landed on a non-present entry
— precisely the "plausible wrong translation or reserved-bit #PF, and NOTHING names which" the plan's
**C5** describes, reached by a corpus stub rather than by a guest.  Two consequences worth carrying:

* the stub was fixed to `mov eax, 0x100 # EFER.LME (bit 8; bit 0 is SCE, NOT this)`, after which every
  case stops at S2's named refusal (the census above);
* **S2's refusal is correctly conditional**, and this episode is the evidence: a guest that sets PAE
  and PG WITHOUT LME is asking for plain 32-bit PAE paging, and refusing that would be wrong.  What
  the port cannot survive is LME+LMA with a 3-level walk, and that is what it refuses.

### 4.2 THE ABRIDGED FTW IS A VALID MASK, AND THIS SLICE READ IT BACKWARDS (round 2, fixes 2-4)

**The claim in round 1 was false and is retracted.**  It said the fxsave abridged FTW "reads
0xFF in every state we produced" and concluded the field was dead, then derived the tag word
from the slot VALUES with a "a slot holding exactly 0.0 is untouched" rule.  The review
measured the field twice (raw `fxsave`, and the shipped harness on the shipped control image)
and got `swd=0x3800 ftw=0x0080` — bit 7 set, exactly the pushed register.  This pass
re-measured it four more ways, in-process with a plain `fxsave`, and the picture is now
unambiguous (MEASURED, Ryzen 9 3950X):

| state | swd | top | ftw | registers holding values |
|---|---|---|---|---|
| `fninit` | 0x0000 | 0 | **0x00** | none |
| `fninit; fld1` | 0x3800 | 7 | **0x80** | physical 7 (logical st0) |
| `fninit; fld1; fld1; fld1` | 0x2800 | 5 | **0xe0** | physical 5, 6, 7 |
| `fninit; fld1; fstp st(0)` | 0x0000 | 0 | **0x00** | none (stale slots 6 and 7) |
| `fninit; movq mm0, [mem]` | 0x0000 | 0 | **0xff** | every register marked |

So on this host **a set bit means the physical register is PRESENT** — AMD's reading of the
abridged FTW (the valid mask); Intel documents the inverse.  The round-1 conclusion came from
reading the field with Intel's polarity: `0x00` looked like "everything present, no information"
when it actually said "nothing present".  An inference from a field read the wrong way round,
stated as a measurement of the field — the exact failure this tree's rules warn about.

**The fix is a CALIBRATION, not a new assumption** (`calibrate_ftw`, `tests/mkfixture64.c`): the
harness does `fninit; fld1` before the fork, reads the byte back (exactly one register is
present — physical 7, logical st0), and recognises the four conventions a host can have
(`0x80`/`0x7f` = physical present/empty, `0x01`/`0xfe` = logical present/empty).  It names the
one it found on stderr (`abridged FTW calibrated: byte 0x80 … bit set means PRESENT, indexed by
PHYSICAL register`) and only a byte matching NONE of the four makes it fall back — loudly, with
the byte printed — to the value-derived rule.  The tag is then the architecture's own:

```
tag(physical p) = (register p PRESENT by the calibrated FTW) ? classify(value) : 2   /* invalid */
```

**What that fixes, on a shipped fixture** (the review's second measurement): `simd-fild-fistp64`
ends with `fistp`, so `top == 0` and **all eight registers are empty**, while slots 6 and 7 still
hold the deterministically stale `1.0` and `6.0`.  Round 1 reported `tag_low = 0x0AAA` with two
registers "live" and **the comparison's MMX branch did not fire**, so that case's `mm` slots were
compared by nothing.  Now it reports `tag_low = 0xAAAA` and every `st` slot `invalid`
(MEASURED) — the branch fires and the `mm` words are compared.  A computed `0.0` is also no
longer mistaken for an untouched register, which removes round 1's named cost entirely.

**Two properties of the corrected derivation, stated so neither is a surprise:**

* an untouched x87 stack now reports `0xFFFFAAAA` — the same sentinel the comparison's gate keys
  on, and **not** "the value 49 of the 123 32-bit fixtures carry" (round 1's claim; fix 4).  The
  measured distribution over this tree's 123 32-bit fixtures is `0xFFFFFFFF` x49, `0xFFFF55AA`
  x22, `0xFFFF56AA` x8, **`0xFFFFAAAA` x7**, `0xFFFF3FFF` x4, and a tail — i.e. **the gate's
  MMX branch fires for 7 of the 32-bit lane's cases**, a property of that instrument worth
  knowing and not a claim about this one.
* after **MMX writes** the hardware marks every register present (`ftw = 0xff`, MEASURED), so an
  MMX case takes the `st` branch, not the `mm` branch.  That is the architecture's answer and
  upstream's rule; the MMX value is still compared where the case stores it to the window
  (`simd-fpu-mmx-64` does exactly that).

**The slot-order claim in round 1 was also backwards** (fix 3).  `st_space` slot `i` is
**LOGICAL `st(i)`** — MEASURED twice: after `fninit; fld1` the `1.0` is in slot **0** (with
`top == 7`), and with `top == 0` a stale `6.0` is in slot 7.  Physical register `p` therefore
lives in slot `(p - top) & 7`, which is `mkfixture.c`'s formula and what the code always did; the
comment claiming physical order was a reader trap that would have invited a breaking "fix".  Both
the comment and `tests/nasm64_run.py`'s mirror of it are corrected.

### 4.3 The corpus's own generator bug: data before the epilogue

The first generated corpus emitted each case's `.quad` data BEFORE the `loop:` label, so execution ran
off the end of the stores into the data bytes: **3 of 57 cases** reported `SIGSEGV`/`SIGILL` on the
native leg (MEASURED: `mov-rip-relative`, `ctrl-lea-64`, `ctrl-push-pop-64`).  After moving the data
past `jmp loop`, exactly the two DECLARED faulting cases (`alu-div-zero` → `SIGFPE`, `ctrl-ud2` →
`SIGILL`) fault, which is the correct census.  This is the shape of finding the tree's rules predict:
a case that faults is not testing what it claims, and the instrument that says so is a per-case
native run — not a build that succeeds.

### 4.4 The trampoline's register allocation, and the FPU state it had to define

The first `jump_to_body` cleared `%rax` and then `jmp *%1`, letting the compiler allocate the entry
address to `%rax`: the child jumped to 0 and every document showed `rip 0x0` (MEASURED).  The entry
now travels through a memory operand into `%r11`, which is the last register the trampoline touches.

The trampoline also has to **define the FPU state**, because there is no `exec`: the child inherits
the parent's x87 and SSE registers, and the parent's `memcpy` leaves the xmm file holding junk
(MEASURED: the first version reported a body's `xmm0-15` as the `memcpy`'s leftovers, so every case
would have compared the harness's own SSE traffic).  `fninit` plus sixteen `pxor`s now put the body
at the state v86 starts from: the all-empty x87 stack and the zero xmm file.

## 5. What this harness CANNOT compare — and which instrument replaces it

The plan's §2.1.5 and §2.2 argue this; the slice makes it concrete, per item, so a gap is never read
as a promise.  **Structurally out of reach** (the host will not run it from ring 3):

| item | why the corpus cannot have it | the instrument that must (plan §2.2) |
|---|---|---|
| `MOV CR*`/`DR*`, `WRMSR`/`RDMSR`, `INVLPG` | a ring-3 process cannot run on a `CR3` of its choosing | spec-derived selftests over `set_cr0`/`set_cr4`/`wrmsr`, one case per SDM rule, each with a mutation probe |
| the 4-level walk's bit composition (P/RW/US/NX/PS, reserved bits), `#PF` error bits | same | the synthetic 64-bit guest image (`pae-guest.asm` shape) + a mutation probe per rule |
| canonicality (`#GP` on a non-canonical linear address) | **partly reachable** — a ring-3 load/store of `0x0000800000000000` faults on the host, and that case belongs in the corpus at S7 | the host for the fault, the synthetic image for the vector and the saved `rip` |
| interrupt/exception DELIVERY, the 64-bit frame, `iretq`, IST, CPL changes | needs an IDT the tracee does not own | the guest (a kernel's first timer tick never returns) + descriptor selftests |
| the 64-bit `GDT`/`IDT`/`TSS` encodings | same | descriptor selftests, one case per field |
| `SYSCALL`/`SYSRET`/`SWAPGS`, `FS`/`GS`-base MSRs, `EFER.LME/LMA/SCE` | privileged | the guest's USERSPACE is the decisive proof; a selftest per MSR field |
| `HLT`/`CLI`/`STI` | privileged (the corpus's `hlt` never executes: the `int3` is first) | the guest gate |
| `CPUID` parity | the host's leaves are the host's; copying them is copying a model nobody chose | the CPUID declaration coupled to the backend's `modes` (§3.5), plus the guest's own refusal |

**Out of reach by RULE** (plan §2.1.5, correction C4): anything the SDM leaves undefined — the flags
after a shift by ≥ operand size, the destination of a faulting `CMPXCHG16B`, the partial effects of a
faulting `REP MOVS`.  Those are excluded from the corpus and decided in the port by a stated rule with
a named source.  **A host that happens to do X is not evidence about a model that is allowed to do
Y**, and the corpus's own text is where that stays true.

Three S4-specific blind spots, new to this report and stated so they are not discovered as surprises:

1. **the stub is executed by neither leg** (§2.1) — its tables, its GDT, its far jump are unverified
   until S5;
2. **R8-R15 are zero on the port's side** (the seat) — a case that uses them cannot agree before S5;
3. **the abridged FTW's POLARITY is calibrated at harness start-up** (§4.2): the byte is read on
   this host and the convention named on stderr, so the tag word is the hardware's — but a host
   whose byte matches none of the four known conventions makes the harness fall back, loudly, to
   a value-derived rule (which then skips a computed `0.0`).

## 7. What did NOT land, stated so its absence is not a promise

* **No 64-bit execution.**  Nothing in the model can enter long mode: the stub stops at S2's refusal
  by design, and the corpus is 57/57 RED.  S5 is the first slice that can change a count here.
* **The port's `--fixture64` prints, it does not pretend.**  When the run stops by name (every corpus
  case today) there is no document at all — the refusal IS the named stop, exit 1.  When a run stops
  normally it prints the v2 document AND a stderr note naming the mode when `EFER.LMA` is clear,
  because the register block's high halves are then the S3 projection and r8-r15 do not exist.  The
  alternative (refuse always) would have left the v2 printer untestable until S5; §3's step A is what
  pays for the choice.
* **R8-R15, the wide decoder, REX, `read_imm64`, the long-mode arms of the dispatch table** — S5.
* **The 64-bit engine differential** (interp vs uop, byte for byte) has no subject yet: one engine can
  run long mode and only from S5, so the differential is vacuous until then (stated in the plan too).
* **Nothing about the x87 tag word is left to S10 as a defect**: the FTW polarity is calibrated
  and the derivation is the architecture's (§4.2).  What S10 still owns is the *MMX-after-write*
  case, where the hardware marks every register present and the comparison therefore takes the
  `st` branch — a property of upstream's rule, not a gap in this harness.
* **The corpus is 57 cases, not the plan's ~250.**  The six families exist and are gateable; the growth
  is the later slices' (`--list` prints the census every time the generator runs, and a case with no
  witness cannot be added).
* **No 2 MiB / 1 GiB page in the stub's identity map** (4 KiB only, per plan §2.1.2): the bigger page
  sizes are S11's, and the stub must not use an instruction the slice under test has not landed.
* **Non-canonical `#GP` is NOT in the corpus yet**, although the plan lists it as host-reachable: it
  belongs to the family that can express it (S7's addressing), and adding a case whose expected result
  is a host signal before the port can run anything would only have added a 58th uniform RED.

### 9.2 Fix 2 — the "dead FTW" premise was false

See §4.2: the field is a valid mask, this slice read it with Intel's polarity, and the tag word is
