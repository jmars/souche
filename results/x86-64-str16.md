# x86-64: the 16-bit string forms — the guard LIFTED, and the kernel gets 11,059 instructions further

**Status: the `narrow64` guard on the five 16-bit string forms is lifted, with a corpus case per the
shape that discriminates (a 66-prefixed `rep movsw`), measured to fail against the pre-fix binary; and
the guest runs 11,059 instructions further, to a stop the recursion bound names.**

Every claim is tagged **MEASURED** / **READ** / **INTERPRETATION** / **PROJECTION**.

---

## 1. Which shape, and why (READ + MEASURED)

The guard's own message named its fear: *"66 A5 would otherwise run MOVSQ -- the arms split on F2/F3
only"*. READ (`src/cpu/interpreter_gen.c`, `case 0xA5:`) shows the arm the 0x66 prefix actually
reaches:

    case 0xA5:
        if (long_mode_64()) { unimplemented(...); return; }        <- the guard
        if (prefixes & F2) instr16_F2A5(); else if (F3) instr16_F3A5(); else instr16_A5();

**The 0x66 arm calls the 16-bit bodies** (`instr16_A5` → `movsw_rep` → `string_instruction(…, STR_W,
…)`), and those go through the long-mode path the rep-string unit built (64-bit RSI/RDI/RCX, DF, the
ZP exit, partial effects kept). **So the fear was misplaced:** `dispatch_os_index` returns **0** for a
0x66 prefix (it is not REX.W and not default-64), so the 0x2NN arm — the one that would run `MOVSQ` —
**cannot** be selected here. **The guard was lifted, not the bodies duplicated**, and the note left in
the overlay records exactly that reasoning.

## 2. The arm (MEASURED to fail before, pass after)

New corpus case **`str/word-forms-66`** — the corpus *can* carry this one (a string op is
unprivileged, unlike `mov cr4`): `66 F3 A5` = `rep movsw` with **three** elements over a qword of data,
then `rep stosw`, then `repe cmpsw`, with RSI/RDI/RCX stored into the compared window. The width is
the discriminator: a 32-bit fall-through copies four bytes per element and desynchronises everything
after it.

    with the guard lifted:   84/84 green
    with the guard restored: SUMMARY total=84 green=83 red_unimplemented=1     (the case is RED)

| instructions | 4,475,473,445 | **4,475,484,504** (+11,059) |
| stop | `long mode: the 16-bit operand form of a string op in long mode is not implemented (see 0xA5)` | **`a fault raised while delivering a fault: the delivery re-entered four times`** |
| eip | 0xFFFFFFFF9C2771F2 | **0x8AE77246** |
| cr3 | 0x30ea000 | 0x30ea000 (the kernel's own tables) |

**The kernel is past the 16-bit string stop** and runs a further 11k instructions of its own code
before it takes a #PF whose delivery cannot proceed — the recursion bound of the walkoob2 unit firing
again, which is the machine correctly refusing to recurse rather than a host crash.

**So: it does not yet run its own code end to end, but the stop that blocked it is gone and the guest
is deeper into the kernel than at any point in this lane.**

## 4. The next unit, named

**The #PF at `eip=0x8AE77246`** — a fault whose *delivery* faults again. The toolkit answers it in one
flag (`V86C_WATCH` + `V86C_DUMP_ON_STOP=1 V86C_CHAIN=<the faulting address>`): the same shape the
gsfix unit used to localise the last one, and the IDT question of the deliver unit applies again (is
the gate's page mapped this time?). **That is the first measurement**, not a guess.
