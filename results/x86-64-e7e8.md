# x86-64: the new stop is `ltr %eax`, and the GDT base is truncated to 32 bits on the way to the descriptor

**Status: MEASUREMENT + ROOT CAUSE (three port runs, no source change). The stop is the SAME CLASS as
this lane's earlier 32-bit-destination truncations, in a new place: `lookup_segment_selector` drops the
top half of the 64-bit GDT base. It is NOT a one-line fix, so it is named, not landed.** Claims tagged
MEASURED / READ / INTERPRETATION.

## 1. Symbolicated (MEASURED)

The stop's `rip` is KASLR-slid. `nokaslr` gives the link address directly:

    KASLR run:   rip=0xffffffff88e7e8d4  cr2=0xc0a0b010  gs_base=0xffff8c16c0a00000
    nokaslr run: rip=0xffffffff8107e8d4  cr2=0xa0b010    gs_base=0xffff888000a00000
    slide = 0x88e7e8d4 - 0x8107e8d4 = 0x7E00000   (the same delta this lane measured before)

`objdump` at `0xffffffff8107e8d4` in `/tmp/vmlinux.bin`:

    ffffffff8107e8b5: mov  %gs:0x199e0(%rip),%ebx    ; this_cpu_read(...)
    ffffffff8107e8bc: sgdt 0x6(%rsp)
    ffffffff8107e8c8: cmp  0x8(%rsp),%rax            ; the GDT base the CPU actually has
    ffffffff8107e8cd: je   0xffffffff8107e8f1        ; ... vs the per-cpu one: skip if equal
    ffffffff8107e8cf: mov  $0x40,%eax
    ffffffff8107e8d4: ltr  %eax                      ; ← the faulting instruction, selector 0x40

That is the kernel's per-cpu GDT reload (`cpu_init`'s `load_TR_desc()`): `ltr` with the TSS selector
`0x40`, i.e. the descriptor at `gdtr_base + 0x40`.

## 2. The access, and why it is unmapped (MEASURED, `V86C_WATCH`)

    WATCH F 0xa0b040 read rip=0xffffffff8107e8d4 (the access FAULTED, no store)

The **first** fault is a read at linear **`0xa0b040`** — which is `gdtr_base + 0x40` **with the top 32
bits dropped** (`gdtr = 0xffff888000a0b000`; `0xffff888000a0b040 & 0xffffffff = 0xa0b040`). The chain is
not absent and the frame is not outside RAM: `0xa0b040` is *inside* RAM physically (10.4 MiB), but as a
**linear** address it is user-space in the kernel's page tables and has no mapping, so the read is a
`#PF` — and every later fault in the run is the same page (`0xa0b010`, the recursion's re-entry; that is
what `cr2` ends up holding, which is why the KASLR run's `0xc0a0b010` looked like a per-cpu address).

## 3. Root cause (READ, `src/cpu/exceptions.c:951-986`)

```c
    uint32_t table_offset;
    if (seg_selector_is_gdt(selector)) {
        table_offset = (uint32_t)cpu->gdtr_offset;      /* ← the 64-bit GDT base, truncated */
        ...
    }
    int32_t address = (int32_t)seg_selector_descriptor_offset(selector) + (int32_t)table_offset;
    uint32_t physical = translate_address_system_read(address);   /* this already takes a uint64_t */
```

`gdtr_offset` is a `uint64_t` (the port stores the full base — `instructions_0f.c:256`), and
`translate_address_system_read` already accepts a 64-bit address; the truncation is the two casts in this
function. LDTR's base (`cpu->segment_offsets[LDTR]`) is truncated the same way on the other branch.

## 4. One sentence on the class

**Same class as this lane's earlier 32-bit-destination truncations (not the flags class): the
instruction form is `ltr r/m16` — `0F 00 /3`, selector `0x40` — and its descriptor fetch goes through
`lookup_segment_selector`, which hands the walk `0xa0b040` where `0xffff888000a0b040` is required.**

## 5. Why the fix is NOT landed here

It is not one line. The out-parameter is `int32_t *descriptor_address` and it feeds **seven** call sites
(`exceptions.c:355, 418, 597, 669, 721, 1016, 1645, 1757`), two of which already truncate again
(`read64s((uint32_t)descriptor_address)`, lines 602 and 614) and one writes the accessed bit through
`translate_address_system_write(descriptor_address + 5)` (line 1096); the recording definition in
`cpu_selftest.c:1680` must follow. And the arm this needs — a GDT base above 4 GiB in long mode, asserting
that `ltr 0x40` reads `gdt_base + 0x40` — is not something the current harness builds (its GDT sits in
low memory). That is a unit of its own, with the 32-bit corpus as the risk surface; landing it on a
measurement-only budget would be the "fix you cannot prove" the brief forbids.

## The ONE next measurement (the next unit's whole job)

**Widen the descriptor-address path to 64 bits**: `lookup_segment_selector`'s `table_offset`/`address`
and the `descriptor_address` out-parameter (plus the two `read64s((uint32_t)…)` reads and the
`translate_address_system_write(descriptor_address + 5)`), with an arm that places the GDT above 4 GiB in
long mode and asserts the descriptor is read at `gdt_base + 0x40` — then the guest should get past
`cpu_init`'s `ltr`, and the next stop will be new again.
