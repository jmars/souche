# x86-64: the 64-bit stack path — widened and measured, and the crash moved into the page walk

**Status: the stack path now carries the whole 64-bit RSP (MEASURED), the 32-bit-stack named stop is
gone, and the guest still dies with a HOST SIGSEGV at the same instruction — now *after* the stack
arithmetic, inside the frame read on a kernel virtual address. That site is named and not fixed.**

Every claim is tagged **MEASURED** / **READ** / **INTERPRETATION** / **PROJECTION**.

---

## 1. What was widened (MEASURED)

`misc_instr.c`'s four stack helpers each gained a long-mode arm **ahead of** their existing ones, so
the 16/32-bit arithmetic is untouched:

| helper | before | now, in long mode |
|---|---|---|
| `get_stack_pointer(offset)` | `int32_t`, `get_seg_ss() + read_reg32(ESP) + offset` | **`int64_t`**, `get_seg_ss() + read_reg64(ESP) + offset` |
| `adjust_stack_reg(n)` | `write_reg32(ESP, …)` | **`write_reg64(ESP, …)`** |
| `get_stack_reg()` | `int32_t`, `read_reg32(ESP)` | **`int64_t`**, `read_reg64(ESP)` |
| `set_stack_reg(v)` | `write_reg32(ESP, v)` | **`write_reg64(ESP, v)`** |

The full-width address then flows into the resolver unchanged, because `safe_read*/safe_write*` have
taken `int64_t` since the "widen the bodies" unit — the same shape, applied to the stack.

**MEASURED (probe at `instr64_CB`, since removed):** the kernel's third RETFQ now computes

    PROBE retfq: rsp64=0xffffffff9bc03f40 addr=0xffffffff9bc03f40

— the address the resolver receives **is** the 64-bit RSP. The old code produced `0x9bc03f40` there.

## 2. The out-of-bounds guard: removed, and where the bound now lives (MEASURED / READ)

The last unit's guard (`instr64_CB`: `if (read_reg64(ESP) > 0xFFFFFFFF) → named stop`) is **removed**,
not disabled: with the stack path widened, a kernel stack at `0xFFFFFFFF9BC03F40` is an *ordinary*
address at that instruction, so keeping the check would be a **false stop on a valid guest state** —
exactly what the brief asked to distinguish. The comment left in its place says so.

**Where the bound still is, and why that is the right place:** a *physical* address out of range is
caught by the machine's own limits — `interpreted_run`'s fetch guard
(`phys_addr >= cpu->memory_size` → named stop) and the 4-level walk's `WALK64_TABLE`/frame bound
(paging.c:448-457: a page-table read or frame outside guest RAM is a named stop). **The distinction
is linear vs physical:** a 64-bit *linear* address is now legal (that is the guest's own address
space); a *physical* address outside RAM is still a named stop.

## 3. The guest: still a host crash, and it moved (MEASURED)

    $ ./build/v86c --bzimage tests/images/vmlinuz-6.1.0-50-amd64 4475480800 … --long-mode on
    Segmentation fault (core dumped)          # 139, and NO "HOST FAULT" dump

The crash is at the same instruction (the kernel's high-stack RETFQ, ~4,475,480,768), but the probe
proves the stack arithmetic is no longer the cause: the address handed to the resolver is correct.
So the crash is inside `safe_read64_addr(0xFFFFFFFF9BC03F40)` — the 4-level walk on the **kernel's own
page tables** (`cr3 = 0x30ea000`), i.e. the PML4 index 511 path.

**INTERPRETATION, and stated as one:** the walk's table-read and frame bounds exist (READ above), so
the remaining candidates are a *frame* that passes the 32-bit bound check but is dereferenced through
a wider access, or a walk path that bypasses the macro. **The next measurement is named:** instrument
`do_page_walk64` for exactly this address — print each level's entry address, its value, the frame it
produces and which bound (if any) it passed — and the crash site becomes a line rather than a guess.
A crash is a defect in this port's contract (it must always name a stop), so it is the next unit's
first job, not a footnote.

## 4. The corpus question, answered (READ)

**The corpus cannot carry a high-RSP case, and for a *different* reason than `mov cr4`.** `mov cr4`
failed because the native leg is CPL 3 and the instruction is privileged. A high stack is *not*
privileged, so a user-mode case *could* in principle run at CPL 3 with `rsp = 0xFFFFFFFF9BC03F40` —
but the corpus harness maps only the flat image at `0x80000` and the compared window at
`0x100000..0x102000`, and a case's stack must be **inside the compared window** for the two legs to
agree on what it wrote. Placing a stack above 4 GiB would need the harness to alias a window page
above 4 GiB in the native leg — harness work, not a case. **So the arm belongs in the selftest**,
and it is **NOT written yet** (stated as a gap rather than implied): the arm is a selftest that sets
`RSP = 0xFFFFFFFF9BC03F40`, pushes and pops, and asserts the *full* register moved — it would fail
against the pre-unit binary by construction, since that binary truncated the address.
