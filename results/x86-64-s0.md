# X86-64-S0 — the backend seam, landed inert

**Unit:** `HANDOFF=v86c-x86-64`, slice **S0** of `results/x86-64-plan.md` (§3.1-§3.4 = the
contract, §3.3 = what is contract and what is not, §3.4 = how the three existing engines land on
it, §6's S0 row = the specification and the gate).  S0 only; S1-S13 are untouched.

**The claim of this slice, in one sentence:** `cycle_internal`'s engine half is now
*a selected backend's `run_batch`* instead of a boolean's `if`, the three engines the port already
had sit behind one contract with no re-implementation of any of them, and **the whole shipped
battery is unmoved** — transcript, corpus, determinism count, bench pin, reboot, VGA and PAE gates
(§5), and, on a real 3G-instruction PAE kernel boot, all four selections produce a
**byte-identical** serial (§5.3).

Every claim is tagged **MEASURED** (run on this host in this pass, command named), **READ** (from
source, with `file:line`) or **INTERPRETATION**.  Decisions are marked as decisions.

## 2. The contract as landed (`src/cpu/cpu_backend.h`)

Exactly the four function pointers, the name and the capability word §3.2 asks for, plus the five
free functions it names and three the *testability* argument in §6 forced (§6.2):

```
name, modes, init, run_batch, clear_caches, print_stats      the struct (6 members)
cpu_backend_select(name)  cpu_backend_current()  cpu_backend_can(mode)  cpu_mode_of(cpu)
cpu_backend_dispatch(phys_addr)   <- cycle_internal's engine half, in ONE callable place
cpu_backend_fallback(b)  cpu_backend_adopt(b)  cpu_backend_by_index(i)
```

`modes` is a family-of-execution-mode bitmask (`CPU_MODE_REAL/PROT16/PROT32/LONG/COMPAT`), not a
feature word: §9 of the plan settles why (the KVM lane keeps this contract with no per-batch flush
points and no 32-bit physical bound).

**What is CONTRACT, and what a backend may not touch** — the §3.3 table, carried into the header
verbatim so the next reader inherits the argument rather than the rule: the reference's *batch
structure* and the counter staircase (the guest's clock is `instruction_counter / 1000` and is
guest-observable), `cpu->in_hlt`, `cpu->reboot_requested`, the stop channel
(`unimplemented_instruction` + its name) and `cpu->pagefault`.  **Implementation detail**:
`uop_pending`, `uop_page_code`, `jit_abort_flag`, `jit_block_boundary`, the arena/pool/recipes —
the dispatcher reads none of them.  **Shared model, outside the contract**: `mem8`, the devices,
the TLB, `cr[]`, the flags, the register file; a backend implements semantics *over* the model,
which is what makes a KVM backend possible at all.

## 3. The three instances are one axis over a cascade, not three peers (C3)

| instance | `run_batch` | the compiled path | `modes` |
|---|---|---|---|
| `interp` | **`interpreted_run`** (the symbol itself, no wrapper) | refused at init, as before | `CPU_MODES_32BIT` |
| `uop` | a 6-line wrapper: `jit_enabled = false` around `uop_run` | **held down for this instance** | `CPU_MODES_32BIT` |
| `uopjit` | **`uop_run`** (the symbol itself) | on — the shipped default | `CPU_MODES_32BIT` |

Nothing re-implements an engine: two of the three `run_batch` pointers *are* the existing
functions, which is also why the selftest can assert them by **pointer identity** rather than
against a table of strings (§6).  The `uop` wrapper exists because §3.4 says the compiled path is
disabled "for this instance": the switch the decode-time compiler reads is a global
(`uop_cache.c:995`), so the instance that owns "no compiled path" holds it down for the duration of
its own run instead of trusting a global some other flag could have moved. Cost: two loads and two
stores per **reference batch**.

## 4. The routing, and the flag

`cycle_internal` (`src/cpu/cpu.c:201`) now calls **`cpu_backend_dispatch(phys_addr)`**, which is:
the mode refusal (`cpu_mode_of` / `cpu_backend_can`, §7), then `current()->run_batch(phys_addr)`.

**`--cpu-engine auto|interp|uop|uopjit`**, and the asymmetry between `auto` and the three names is
a decision (§3.4's own words, made load-bearing):

- **`auto` is the default and DERIVES** from the two existing flags, writing nothing.  So every
  pre-seam invocation keeps its exact behaviour *and its exact stderr* — MEASURED, on the shipped
  binary: `--uop-cache off` still prints `jit: --jit needs the uop cache's invalidation hooks;
  --uop-cache off was also given. JIT off.` followed by the caps line; `--jit off` still prints
  nothing; the default still prints the caps line only.  `--uop-cache on|off` and `--jit on|off`
  therefore stay **aliases** and no gate script changed.
- **An explicit name FORCES** the two booleans (`interp` = off/off, `uop` = on/off, `uopjit` =
  on/on), whatever their order on the command line, and prints `v86c: cpu engine: '<name>'
  (--cpu-engine <given>)` to stderr.  Naming the engine is naming the configuration; a machine
  whose engine and flags disagree is a machine whose stderr lies about what is running.
- An unknown name is refused **by name**, exit 2 (MEASURED: `--cpu-engine kvm` → `v86c:
  --cpu-engine: unknown engine 'kvm' (have: auto, interp, uop, uopjit)`, rc 2).

The other two contract seats got real call sites rather than being declared and forgotten:

- **`init`** — `engine_init_if_needed()` sits exactly where `jit_init_if_enabled()` did (both
  modes, after guest memory exists).  `interp` → nothing to allocate (and it inherits the
  compiled-path refusal, which is what keeps `--uop-cache off`'s stderr unchanged); `uop` →
  `uop_cache_init()`; `uopjit` → `jit_mem_init()`.  A `false` is the contract's refusal: the
  machine adopts `cpu_backend_fallback()` (uopjit → uop → interp) **and says so by name**.
- **`clear_caches`** — `reboot_prepare_reentry()`'s two statements became
  `current()->clear_caches()`; the caches are the *machine's* (every guest write goes through the
  same invalidation hooks whatever engine is selected), which is why all three instances point at
  the same body.
- **`print_stats`** — `--uop-cache-stats` now asks the engine; the compiled path's counters stay
  on their own flag line (`--jit-stats`), which is why the output is byte-identical to pre-S0 in
  all four flag combinations.

### 5.1 Attribution when a byte moves

- `results/pae-l3-c-serial.txt` and `results/pae-l3-js-serial.txt` are **gate outputs**, rewritten
  by every run of `gate-pae-l3.sh`.  The committed copies predate the **VGA lane**: modulo the

## 6. THE INSTRUMENT: and the falsifier work the brief asked for

The plan's own warning is that *a seat that is never called is indistinguishable from an absent
seat*.  S0's instrument is therefore in **two halves**, because one suite cannot reach both ends —
and that split is the finding of this section, not a caveat bolted on at the end.

### 6.1 Half one — `cpu_selftest.c`'s `test_cpu_backend()` (58 checks)

1. **the resolver**: each of the three names selects an instance whose `->name` is that name and
   `cpu_backend_current()` agrees;
2. **the `run_batch` SYMBOL, by pointer identity against the real symbols**: `interp` **is**
   `interpreted_run`, `uopjit` **is** `uop_run`, `uop` is neither, and the three pointers are
   pairwise distinct;
3. **the round trip, both directions**: instance → the two flags → `select("auto")` → the same
   instance.  A selection that resolved everything to one instance dies here;
4. **the dispatch is CALLED**: `cpu_backend_dispatch(0x12345)` — the function `cycle_internal`
   calls — with `interp` selected, and the address asserted to arrive at `interpreted_run`
   (the stub records one call and returns for exactly this check; it still aborts from anywhere
   else, so the suite's "this binary has no run loop" premise survives);
5. **the capability word**: the three 32-bit modes declared, **no long mode anywhere**, and
   `cpu_backend_can(cpu_mode_of(cpu))` true — the refusal seat's own precondition;
6. the fallback cascade, the by-index enumeration, and that an unknown name returns `NULL`
   **without half-selecting**.

### 6.2 Half two — `make engine-identity` (new, run by `make selftest`)

Why a second instrument: **the C suite has no run loop**, so it cannot show that the selection
changed *which code ran*.  `engine-identity` runs the shipped binary once per engine and reads the
**engines' own counters** (`--uop-cache-stats` / `--jit-stats`), which is the only thing that
separates the three selections at execution level (MEASURED):

```
engine-identity: lookups interp=0 uop=130 uopjit=133;
                 compiled interp=0 uop=0 uopjit=4
engine-identity: the three selections are observably different (gate passed)
```

`interp` never runs the decoded-block cache; `uop` runs it with the compiled path held down
(`blocks compiled 0`); `uopjit` runs it with the compiled path on (`4`).  The target asserts the
**shape** (zero / positive-and-uncompiled / positive-and-compiled), not three pinned numbers —
those counts belong to the guest image, and a change to them would be another unit's finding.

### 6.3 The falsifier: I mutated the code and checked BOTH instruments bite

Each mutation was applied to `src/cpu/cpu_backend.c`, rebuilt, run, and reverted (the binary's
sha256 returns to `fee8c1a2605e9617…`, MEASURED):

| mutation | `cpu_selftest` | `engine-identity` |
|---|---|---|
| **B** an explicit selection forces only one of the two flags (`force_flags` half a no-op) | **3 failures** (`jit_enabled == i == 2` ×2, `select("auto") == instance[i]`) | passes |
| **C** two instances collapse onto one `run_batch` (`uopjit` loses the compiled path) | **2 failures** (`instance[2]->run_batch == uop_run`, `instance[1]->run_batch != instance[2]->run_batch`) | passes |
| **D** the dispatcher ignores the selection (`cpu_backend_dispatch` hard-wires `interpreted_run`) | **0 failures — it does NOT bite** | **FAILS**, named: `engine-identity: 'uop' did not run the decoded-block cache` (lookups 0 instead of 130) |

Row D is the honest limit stated as a measurement: the selftest alone cannot see the routing,
because it can only drive the one engine whose body is a stub in that binary.  Rather than word the
claim down to what the suite covers, S0 ships the second instrument that *does* bite on it — and
that is why `engine-identity` is a prerequisite of `make selftest` rather than a report footnote.

## 7. What did NOT land (so its absence is not read as a promise)

- **The mode refusal is INERT BY CONSTRUCTION in S0.**  `cpu_backend_dispatch` asks
  `cpu_backend_can(cpu_mode_of(cpu))` before every batch and stops **by name**
  (`"cpu backend 'interp' cannot run long mode"`), but no engine declares a mode the machine can
  be in: `cpu_mode_of` returns real / 16-prot / 32-prot only, because `EFER_LME` is not defined
  anywhere in this tree (plan finding 5) and long mode does not exist.  An instrument that cannot
  fail is not a test — **S2 owns the probe that makes it fire** (§6's S2 row, and §3.5's CPUID
  declaration).
- **Long mode, the widened state, the 64-bit decoder, the corpus, the system layer, the guest and
  the engines' long-mode arms are S1-S13**, unstarted.  `results/x86-64-plan.md` is the plan of
  record; `TODO.md` §8 records what is left.
- **C5 (the live defect: `EFER.LME` dead, `wrmsr(EFER)` unchecked, so `LME`+`CR0.PG` takes a
  3-level walk over 4-level tables) is still live.**  It is S2's, and S0 changed no behaviour that
  could close it: this slice added the *seat* the refusal will sit in, not the refusal.
