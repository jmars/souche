# x86-64: the `jz` is innocent — the LA57 mystery is SOLVED, and the stop is a different #GP

**Status: the third measurement answers the LA57 question completely. `test_z()` is 1 at the branch,
the branch IS taken, CR4 is written as PAE|PGE (no LA57) — and the port STILL #GPs on that write.
The LA57 bit was a *symptom* of the RIP-relative defect fixed in the previous unit, and the previous
unit's conclusion that the two were unrelated is CORRECTED here.**

Every claim is tagged **MEASURED** / **READ** / **INTERPRETATION** / **PROJECTION**.

---

## 1. The flag state, instruction by instruction (MEASURED)

A probe at each eip in `0x1000083..0x1000099` printed `cpu->flags`, `cpu->flags_changed`, **the
getters themselves** (`getzf()`, `test_z()`), and the lazy operands:

| eip | op | flags | changed | getzf | test_z | last_op1 | last_result | op_size |
|---|---|---|---|---|---|---|---|---|
| 0x1000083 | 0F | 0x6 | 0x8D5 | 0 | 0 | 0 | 0xAEEA000 | 63 |
| 0x1000086 | 83 | 0x6 | 0xC4 | **1** | **1** | 0 | 0 | 31 |
| 0x1000089 | 81 | 0x6 | 0xC4 | 0 | 0 | 0 | 0xA0 | 31 |
| 0x100008F | F7 | 0x6 | 0xC4 | **1** | **1** | 0 | 0 | 31 |
| **0x1000099** | **74** | 0x6 | 0xC4 | **1** | **1** | 0 | 0 | 31 |

**At the `jz` the condition is TRUE.** The lazy ZF is stale (`flags_changed & FLAG_ZERO` set) and the
getter computes `(~0 & (0-1)) >> 31 & 1 = 1` — correct. Nothing in the flag machinery is wrong:
`test32(0, 1)` set the stale state, `getzf()` recomputed it, and `test_z()` returned it.

## 2. CORRECTION: the branch IS taken, and the LA57 bit is GONE (MEASURED + one INTERPRETATION)

The previous unit's eip trace (`0x1000099 → 0x100009B`, fall-through) was taken **before** the
RIP-relative fix, when the `test` read `0x2413D6C` (four bytes early, nonzero) and legitimately left
ZF clear. With the fix in place the same branch now reads the correct zero dword and `test_z()` is 1,
so the `or ecx, 0x1000` at 0x100009B is **skipped**.

**INTERPRETATION, stated as such:** the `mov cr4` therefore receives **0xA0 (PAE|PGE)**, not 0x10A0.
It follows from the measured branch plus the instruction sequence at 0x1000089/0x100009B; the
register was not re-read in this run, so it is an inference from a measurement and is labelled one.

**So `results/x86-64-la57.md`'s conclusion — "this defect is real and is not the LA57 cause" — was
WRONG. It was the cause:** the LA57 bit was the wrong-way branch, and the wrong-way branch was the
four-byte-early read. The gp report's candidate 1 (wrong CPUID), candidate 3 (the kernel wrote the
variable) and the "flags read wrongly" hypothesis of this unit's brief are **all refuted** — the flags
are fine, the variable is 0, CPUID advertises nothing.

## 3. The stop that REMAINS is a different one: `mov cr4, 0xA0` still #GPs (MEASURED)

    v86c boot: 4475480658 instructions, unimplemented=1, eip=0x10000a1
    v86c: unimplemented: call_interrupt_vector: invalid gate type 0 for vector 13
          (idtr base 0x2a04000 limit 511, descriptor at 0x2a040d0 = 0x0,
           faulting rip 0x10000a1 bytes 0f 22 e1 48 03 05, cpl 0 cr2 0x0 cr3 0x4f76000)

`0xA0` has bits 5 (PAE) and 7 (PGE). The port's reserved-bit mask
(`1<<11|1<<12|1<<15|1<<16|1<<19 | 0xFFC00000`) does **not** contain either, so the #GP comes from a
later step of the same instruction. READ (`src/cpu/instructions_0f.c`, `case 4:` of MOV CRn): after
the mask check the port compares `old_cr4 ^ data` against `CR4_PAE | CR4_PGE | CR4_PSE | CR4_SMEP`
and, when that differs, **reloads the PDPTEs** — the SDM's rule for a MOV to CR4 — and a PDPTE with a
reserved bit set raises #GP. Here `old ^ new = 0x80` (PGE) so that path runs, and it is the branch
that fires.

**INTERPRETATION:** in IA-32e mode the reload must read the **PML4E** named by CR3, and its reserved
bits are `63:52` (with the NX bit legal at 63); a 4-level PML4E the guest built for long mode has
none of them set, so a #GP here means the port is checking the wrong bits or reading the wrong entry.
That is the next thing to measure, not to assume.

## 4. The next measurement, named

Probe the CR4 write path itself: log which branch of `case 4:` raises the #GP (the mask check vs the
PDPTE reload), and dump the PML4E/PDPTE the reload reads (`cr3`, the entry's address and value, and
which bit the port calls reserved). That distinguishes "the reload's reserved-bit mask is the 32-bit
PAE one applied in long mode" from "the entry read is wrong". **A second, independent check worth
having at the same time:** a corpus case that writes CR4 = PAE|PGE in long mode from a clean state
(`mov rax, 0xA0; mov cr4, rax`) — if that #GPs in isolation, the defect is reproduced without the
kernel, exactly as the RIP-relative one was.
