# x86-64: the E820 the PORT's firmware publishes, as the kernel reads it

**Status: MEASUREMENT (a), PORT SIDE ONLY. No source change, no fix, no battery. The QEMU leg at
256 MiB is NOT in this unit.** Every claim tagged MEASURED / READ / INTERPRETATION.

Run (MEASURED, one run, 1m58s wall, exit 1 = the same delivery fault as the handoff's stop):
`V86C_BOOTPARAMS=0x84790 V86C_DUMP_ON_STOP=1 ./build/v86c --bzimage tests/images/vmlinuz-6.1.0-50-amd64
6000000000 --memory 256 --cmdline 'console=ttyS0 earlyprintk=serial' --serial /tmp/e820-port.txt
--long-mode on`. **READ: `V86C_BOOTPARAMS` ALONE PRINTS NOTHING** — it is dumped from
`v86c_dbg_on_stop` (`src/cpu/debug.c:371-406`), which returns early unless `V86C_DUMP_ON_STOP=1`.
`0x84790` is the zero page address the previous bootparams unit used; the dump read it back intact.

| # | base | len | type | bytes |
|---|---|---|---|---|
| 0 | `0x00000000` | `0x0009fc00` | 1 RAM | 0–639 KiB |
| 1 | `0x0009fc00` | `0x00000400` | 2 reserved | 639–640 KiB |
| 2 | `0x000f0000` | `0x00010000` | 2 reserved | 960 KiB–1 MiB |
| 3 | `0x00100000` | `0x03f00000` | 1 RAM | 1 MiB–**64 MiB** |

`e820_entries=4`, `alt_mem_k=0x0`, `setup_sects=39`, `init_size=0x3f97000`. The kernel's own serial
`BIOS-e820:` lines are byte-for-byte these four ranges (MEASURED, `/tmp/e820-port.txt:15-18`), so the
table above is what the kernel actually consumed, not a loader-side artifact. The firmware's source
(`tests/minibios.asm:803-807`) holds the same four entries with `MEM_TOP` assembled in as `0x4000000`
(64 MiB, `tests/minibios.asm:54-56`); `--memory 256` does **not** rebuild the firmware
(`src/main.c:783-793`) — READ.

**ANSWER, one sentence: NO entry claims RAM above 256 MiB — the map's usable top is 64 MiB, i.e. the
kernel is told the machine is SMALLER (63 MiB usable) than the 256 MiB it actually has, the opposite of
the ~3.2 GB belief this unit was sent to explain.**

**INTERPRETATION (the premise this measurement refutes, and the third measurement it names).** The
3.2 GB does not come from the E820. In this same run the kernel reports `last_pfn = 0x4430`
(`0x4430000` = 68.2 MiB, serial:27), fakes node 0 at `[mem 0x0-0x442ffff]` (serial:35), and allocates
`NODE_DATA(0) at [mem 0x00fd4000-0x00ffefff]` (serial:36) — all well inside RAM. `0xc0fd4000` and
`0xc0e00000` are therefore the **low 32 bits of the virtual** values `0xffff8c16c0fd4000` /
`0xffff8c16c0000000 + 0xe00000`, not physical addresses above RAM: at the stop, `cr2=0xc0a0b010` while
`gs_base=0xffff8c16c0a0b000` (MEASURED, `/tmp/e820-port.out:6-8`), the same 32-bit drop. **The third
measurement is the one to take next: watch the page walk / fault-path store that carries a 64-bit
linear address into a 32-bit slot (cr2, the PTEA/PDE base, or `__per_cpu_offset`), not the E820 and not
the firmware.** Naming it rather than choosing: (a) says the map is 63 MiB, so (a) cannot be the
producer of a 3.2 GB phys.
