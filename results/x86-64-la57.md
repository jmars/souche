# x86-64: the LA57 question — the writer is neither CPUID nor the kernel, and a real RIP-relative defect fell out

**Status: the two measurements are done and they REFUTE two of the three candidates. A real,
separate port defect was found and fixed on the way (`RIP`-relative base with a trailing immediate,
four bytes early), with an arm that fails before and passes after. The LA57 branch itself is STILL
UNEXPLAINED and the guest stops at the same instruction — that is recorded, not papered over.**

Every claim is tagged **MEASURED** / **READ** / **INTERPRETATION** / **PROJECTION**.

`results/x86-64-gp.md` named the variable's address as `0x2143D6F`, from hand arithmetic on the
`test`'s displacement. **That was wrong twice** (0x2143D6F, then 0x2143D70). The instruction is

**The correction is recorded rather than quietly re-pinned**: two hand-computed addresses in the
previous report were wrong, and the third measurement was designed to be self-checking because of it.

At the CR4 write the probe read the variable three ways and they agree:

    PROBE translation: linear 0x2413D70 -> phys 0x2413d70; safe_read32s=0x0;

**So `__pgtable_l5_enabled` is 0 when the kernel tests it.** Candidate 3 (the kernel wrote it, or the
kernel decided LA57 is on from its own state) is **REFUTED**: the kernel's variable is zero, and the

## 3. Measurement (2): the CPUID dump — no LA57 anywhere (MEASURED)

Called through the port's own `instr_0FA2` at the end of the run, at every subleaf:

    PROBE cpuid(0,0):   eax=0x16 (max level)  ebx=0x756e6547 ecx=0x6c65746e edx=0x49656e69
    PROBE cpuid(7,0):   eax=0x0  ebx=0x200  ecx=0x0  (LA57 bit16 = 0)  edx=0x0
    PROBE cpuid(7,1):   eax=0x0  ebx=0x0    ecx=0x0  edx=0x0

Candidate 1 (a wrong CPUID answer) is **REFUTED**: leaf 7 advertises no LA57 at either subleaf, and
the port's unsupported-subleaf answer is all zeros as the SDM requires. The kernel's
`native_cpuid_eax(0) >= 7 && (native_cpuid_ecx(7) & (1 << 16))` is therefore **false**, which is
consistent with §2's zero variable — and inconsistent with the LA57 bit the kernel puts in CR4.

**Where the LA57 bit comes from is still open.** The eip trace at the CR4 write (MEASURED) shows the
`jz` at 0x1000099 **falling through** to `or ecx, 0x1000`:

    PROBE last 10 eips at the CR4 write: 0x1e01d30 0x100005f 0x1000060 0x1000066 0x1000083
                                         0x1000086 0x1000089 0x100008f 0x1000099 0x100009b

with the operand measured 0 and the address measured correct. So the remaining suspect is **the
flags the `jz` reads after `test dword [mem], 1`** — not the memory, not the address, not CPUID.

## 4. The defect the measurements DID expose: the RIP-relative base was four bytes early (MEASURED, FIXED)

While deriving the address from the instruction bytes, the `F7 05 disp32 imm32` encoding made a real
port bug visible: `modrm_resolve64` computes the RIP-relative base as
`cpu->instruction_pointer + disp`, and at that moment the cursor sits **after the displacement** —
because the port reads the immediate *after* resolving the address (upstream's argument order, which
is semantic and is kept). For an instruction with a **trailing immediate** the base must be the
address of the **next instruction**, i.e. after that immediate: four bytes later for an imm32, eight
for an imm64.

**The fix:** `modrm_resolve_imm(modrm_byte, imm_bytes)` — the emitter passes the trailing immediate's
size (0 when there is none, derived from the same `gen_read_imm_call` decision that emits the read),
and the RIP-relative branch adds it. 158 emitted arms now carry a non-zero size.

**The arm that fails before and passes after (MEASURED):** new corpus case
`ctrl/rip-relative-with-imm` — `test dword ptr [rip + body_data1], 1` where `body_data0`'s **high**
dword is 1 and `body_data1` is 0, so the correct target sets ZF (JZ taken, r8 stays 0x1111…) and a
four-byte-early read finds 1 (JZ not taken, r8 becomes 0x2222…). With the fix: **83/83 green**. With
the trailing-immediate term removed (`/* MUTATION */`): `total=83 green=82 mismatch=1`,
`ctrl-rip-relative-with-imm.img: 7 field(s)`, `reg64[8] (r8) actual 0x2222222222222222 expected
0x1111111111111111`. The first version of the case did NOT discriminate (the data block is `.quad`,
so the early read landed on a zero high half) — that is recorded because a non-discriminating arm is
the failure mode this lane has been burned by.

**This defect is real and is not the LA57 cause:** with the fix the guest runs four instructions
further (4,475,480,654 → **4,475,480,658**) and stops at the **same** `mov cr4, rcx` at 0x10000A1
with the same `idtr base=0x2a04000 limit=511`. Said plainly: one real bug fixed, the LA57 question
unchanged.

## 5. The third measurement, named

The memory is proven 0, the address proven correct, CPUID proven clean, and the `jz` still falls
through. The next measurement is therefore **the flags at the branch**: a probe at `0x1000099`
printing `cpu->flags` and `cpu->flags_changed` immediately after the `test` at `0x100008F`, plus the
same pair for a corpus case that reproduces the kernel's exact RIP-relative-with-immediate `test`
against a zero dword followed by `jz`. That distinguishes "`test32` did not set ZF" from "`jz` read
the wrong flag", which is the only fork left.
