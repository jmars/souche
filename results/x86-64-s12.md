# X86-64-S12 — the guest: the amd64 kernel boots into long mode and stops at a NAMED piece

**Unit:** `HANDOFF=v86c-x86-64-s12`, slice **S12** of `results/x86-64-plan.md` (§6's S12 row, §2.3
the guest layer, §5.3 the boot path). S0-S11 are landed; S13 untouched.

**The finding, one sentence — and it is the plan's own falsifier, not a regression:** a **pinned
Debian amd64 kernel** boots on the port under `--long-mode on`, **enters long mode, builds its own
page tables and executes 64-bit code** (`eip=0x100208 cs=0x10 cr0=0x80050033 cr3=0x4f76000`), and
then stops at a **NAMED** system-layer piece: **`call_interrupt_vector: invalid gate type`** — the
64-bit IDT gate / interrupt frame, which S11 named as its first item and which the turn cap did not
reach. **The guest does not reach userspace, and this report says exactly how far it got with the
kernel's own serial output as the evidence.**

The shipped binary did **not move** (`021c0929…`, S11's): S12's landed artifact is the **vehicle and
its gate**, and the boot path needed **no code change** — which is itself a measured result
(§3.1).

## 2. The gate: `tests/gate-x86-64.sh` (new, **7 passed / 0 failed**)

Each step an exit code; the shape is PAE-L3's (pin, refusal, progress, honest stop):

| step | what it asserts |
|---|---|
| A `kernel-sha256` | the committed image is the pinned one |
| B `no-long-mode-refuses` | **the flag is OFF by default**: without `--long-mode` the amd64 kernel is **refused by name** at its first IA-32e write (`cannot run long mode`) — the capability is a declaration, not a default |
| C `kernel-runs` | the kernel executes (the port's boot line reports an instruction count) |
| C `kernel-in-long-mode` | **`cs=0x10 cr0=0x80050033`** — the kernel's own data selector and control-register state |
| C `kernel-page-tables-in-ram` | **`cr3=0x4f76000`** — the kernel built its own page tables, inside guest RAM |
| C `kernel-serial-output` | the kernel's **own** serial line (`Probing EDD … ok`) |
| D `stop-is-the-64bit-interrupt-frame` | the stop is **`call_interrupt_vector`**, by name |

**Step D is the honest seat.** It asserts that the guest stops **there** — a stop *earlier* is a
regression and a silent hang is a defect — and when the interrupt frame lands, **that step is
replaced by the userspace assertion, visibly**. A gate that demanded userspace today would be red
and uninformative; one that ignored the stop would be a reworded claim.

## 3. What the boot measured, and what it did NOT need

### 3.1 The boot path needed NO code change

Plan §5.3's INTERPRETATION — "an x86-64 bzImage starts its setup in 16-bit real mode and enters long
mode itself, so `minibios` and `kernel.c` are unchanged" — is now **MEASURED**: the same firmware,
the same `--bzimage` path, and the kernel's own setup code performs the IA-32e transition (it is the
guest's `wrmsr(EFER.LME)` + `CR0.PG` that S2's refusal guards). The only new flag is
`--long-mode on`, which declares the capability.

### 3.2 The first stop was NOT the system layer — it was MEMORY

With the port's **default 64 MiB**, the kernel's own PML4 landed at physical **`0x4f76000`** (≈79 MiB),
i.e. **above guest RAM**, and S11's table-read bound stopped it **by name**
(`a page-table read at physical 0x4f76000 is outside guest RAM`). With `--memory 256` the same
kernel proceeds to `cr3=0x4f76000` **inside** RAM. **This is a real bound the vehicle must carry**:
the gate pins `--memory 256`, and the report states why (an amd64 kernel's early page tables are
placed high, and the port's physical model is what it is).

### 3.3 The second stop IS the system layer, and it is S11's named gap

`call_interrupt_vector: invalid gate type` — the kernel raised an exception (its early-boot `#PF`
or `#GP` self-test) and the port could not decode the **64-bit IDT gate**. Reading the artifact: the
gate-type test accepts `INTR_GATE_TASK/INTERRUPT/TRAP` (5/6/7, `exceptions.c:536`) and a 64-bit gate's
type field is `0xE`/`0xF`, which **should** mask to 6/7 — so the descriptor the port read is not the
one the kernel wrote, i.e. **the 64-bit IDT base/offset composition is the suspect, not the type
test**; the descriptor's 64-bit offset split (`offset_low | offset_middle << 16 | offset_high << 32`)
and the frame's 8-byte pushes are the same piece. **This is stated as a hypothesis with the evidence
that produced it, not as a diagnosis**: the next unit starts by reading `idtr_offset` and the
descriptor at the stop, which the port's `---BEGIN STATE---` tail already prints.

## 4. NAMED GAPS — what remains before userspace (in the order the guest will need it)

1. **The 64-bit IDT gate decode and the 64-bit interrupt frame** (the stop above): the descriptor's
   offset composition, the IST field, the 8-byte frame pushes, `iretq`. **The gate's step D is the
   instrument**: when it moves, the kernel's next serial lines are the evidence.
2. **The 64-bit GDT/TSS/IST load paths** (`lgdt`/`ltr` with 64-bit descriptors) — the kernel has
   already loaded its own GDT (it is running with `cs=0x10`), so this is partly exercised, but no
   probe asserts the 64-bit descriptor layout.
3. **SYSCALL/SYSRET** (S11's gap): unimplemented encodings; the userspace milestone needs them, and
   the probe is the guest's own first syscall.
4. **SWAPGS** (S11's gap: no `0F 01 /5` entry in the reference table).
5. **The userspace milestone itself** — the initramfs and its evidence printing. **Not built in this
   slice**: it would be the third vehicle piece and the cap did not reach it. The vehicle's shape is
   PAE-L3's reproducible initramfs (`results/pae-l3.md`), and `tests/images/guest-initramfs.img`
   already exists as the i386 precedent — an amd64 rebuild is mechanical once (1) lands.
6. **The QEMU leg** (plan §2.3's second reference): not run in this slice. Cheap to add once the
   guest boots (`qemu-system-x86_64` is on the host, and `tests/gate-m2-5.sh`'s gate 1b is the
   precedent) — and it is the leg that would tell a port defect from a kernel requirement when the
   stop is ambiguous, which §3.3's hypothesis shows it can be.
