## 2. What landed, and the one STATE correction

**`reg_xmm[8]` → `reg_xmm[16]`** (plan correction). Long mode has **sixteen** SSE registers, and a
`REX.B`/`REX.R` register field selects **8-15** — an index the eight-slot array could not hold, so
the accessors would have written **out of bounds**, a guest-reachable host corruption. Indices 0-7
keep their meaning and every 32-bit path is unchanged (the transcript and `nasm` pins say so). The
plan's §4 verdict "`reg_xmm[8]` UNCHANGED" was written before the REX register fields were
reachable; this is the correction.

**Six bodies** (`src/cpu/instructions_64.c`), in two pairs of prefix forms, because the *width* is
what a `REX.W` changes and the semantics are the 32-bit bodies':

| encoding | 64-bit form | what a 32-bit body would get wrong |
|---|---|---|
| `0F 6E` (REX.W) | `movq mm, r/m64` | the low half of the source |
| `66 0F 6E` (REX.W) | `movq xmm, r/m64` | the high half of the xmm destination dropped |
| `0F 2A` (REX.W) | `cvtsi2sd xmm, r/m64` | converts 32 bits of the integer source |
| `F2 0F 2A` (REX.W) | `cvtsi2sd xmm, r/m64` | ditto |
| `66 0F 7E` (REX.W) | `movq r64, xmm` | writes reg32 and zero-extends, dropping the upper half |
| `0F 7E` (REX.W) | `movq r/m64, mm` | ditto |

**The rest of the family needed no new body**: the five cases that were already green went green in
S6, when `modrm_resolve` became mode-aware — the long-mode **addressing** (RIP-relative, 64-bit
SIB, the 64-bit displacement path) is shared, which is exactly what "the addressing and the REX
register fields, semantics unchanged" means.

## 3. The silent-wrong surfaces, named

1. **The 64-bit operand a REX.W selects** — a 32-bit body takes the low half and produces a
   *plausible* wrong value (a wrong xmm register, a wrong double). Instrumented by
   `simd-movq-xmm64` and `simd-cvtsi2sd-64`, and **MEASURED**: a mutant `instr64_660F7E_reg` that
   writes reg32 (the 32-bit body's shape) turns `simd-movq-xmm64` red.
2. **The REX register fields 8-15** — out of bounds on an eight-slot `reg_xmm[]`. Fixed by the
   widening; **no corpus case uses xmm8-15**, so this one is closed by construction and named
   un-instrumented (§5).
3. **The addressing** — RIP-relative and 64-bit SIB in an SSE memory operand. Instrumented by
   `simd-movdqa-64` and `simd-movq-xmm64` (both memory operands at 64-bit addresses), which have
   been green since S6's mode-aware resolver.
4. **The MMX/x87 state handoff** — `transition_fpu_to_mmx()` on every one of the six bodies, as the
   32-bit bodies do; the corpus's `simd-fpu-mmx-64` and `simd-fild-fistp64` compare the tag word
   and the mm registers, so a missing transition moves them.

## 4. What this slice does NOT cover, named rather than implied

- **xmm8-xmm15 as OPERANDS**: the widening makes them representable, but **no corpus case uses
  them** — the REX register-field path for SSE is therefore un-instrumented (a case using
  `movq xmm8, rax` would close it; the corpus's witness rule would accept it as W2).
- **The 0F 6E / 0F 7E / 0F 2A BARE forms** (without `66`/`F2`) have bodies and **no case**; the
  corpus drives the prefixed forms.
- **`movd`/`movq` to/from MEMORY for the mm (not xmm) side** — the `0F 7E` mem body exists, no
  case.
- **Every other SSE/SSE2 encoding** (the arithmetic, the shuffles, the conversions) has **no
  64-bit arm at all**: with REX.W they stop by name. The plan's S10 row scopes the slice to the
  addressing and the register fields, and the corpus contains six cases — so this is a **declared
  boundary**, not an oversight, and the named stops are what keep it from being silent.
- **x87's own encodings** (D8-DF) likewise have no 64-bit arm; the two x87 cases in the corpus run
  through their 32-bit bodies, which is correct because their operands are memory or ST(i) — the
  plan's "semantics unchanged" made concrete.
