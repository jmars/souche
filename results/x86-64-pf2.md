# x86-64: the #PF at 0x8AE77246 — the guest's PML4E[0] is ZERO, so the IDT really is unmapped

**Status: MEASUREMENT ONLY, made entirely with the toolkit — no hand probes, no code change. The
answer is that the guest's own tables lack the mapping (a hand walk and the port's walk read the same
zero), so the delivery re-faults on a genuinely absent IDT page: hardware would #DF and reset, and the
port's named stop is the correct seat. The question that remains is the guest's, and it is named.**

Every claim is tagged **MEASURED** / **READ** / **INTERPRETATION** / **PROJECTION**.

---

## 1. What the first fault is (MEASURED — `V86C_RING` + `V86C_WATCH`)

    v86c dbg: ring: … eip=0xffffffff9c277237 bytes 48 c7 c7 00 76 51 9c b9 00 04 00 00 48 89 de f3
             … eip=0xffffffff9c277243 bytes 48 89 de f3 a5 e8 55 82 97 fe …
    v86c dbg: WATCH F 0x9c5100e0 read rip=0xffffffff9c277246 (the access FAULTED, no store)
    v86c dbg: state rip=0xffffffff9c277246 cr2=0x9c5100e0 cr3=0x30ea000
                     idtr=0x9c510000/4095 gdtr=0x9c24d000/127 cpl=0
    v86c dbg: regs rax=0x0 rbx=0xffff888000084790 rcx=0x400 rsi=0xffff888000084790
                     rdi=0xffffffff9c517600 rsp=0xffffffff9bc03f30

The instruction stream is the kernel's own: `mov rdi, 0x9C517600; mov ecx, 0x400; mov rsi, rbx;
rep movsq` (`f3 a5`) — a 0x400-qword copy — then `call`, then the access that faults. The faulting
access is a **READ of `0x9C5100E0`**, and `idtr = 0x9C510000/4095` makes that address exactly
**`idtr_base + 14*16` — the IDT descriptor for vector 14, read by the delivery itself.**

So the *first* fault is not a guest data access at all: it is the delivery reading its own gate.

## 2. Is the guest's table genuinely absent? (MEASURED — the firstfault unit's method)

    v86c dbg: chain va=0x9c5100e0 cr3=0x30ea000 idx=0/2/226/272
    v86c dbg:   PML4E  @0x30ea000 = 0x0

**`PML4E[0]` is ZERO.** The toolkit's chain walk reads the table bytes physically, and the port's own
walk agrees (it faulted on the same access), so **the port is not wrong here**: no stride, index, frame
mask or truncation is involved — the guest's top-level entry for the entire low half is not present.
(Compare the firstfault unit's reading of the same CR3: `PML4E @0x30ea000 = 0x30EC063` — **the tables
changed between then and now**, which is what early-boot table construction looks like.)

## 3. The delivery, and the seat (INTERPRETATION, on the deliver unit's measurement)

The IDT page is genuinely unmapped, so the delivery's own descriptor read faults, and the recursion
bound stops the machine. Hardware's sequence at this state is `#PF` → the vector-14 gate is read from
an unmapped page → `#DF` → the bringup IDT has no `#DF` gate → **triple fault → reset**. **The port's
named stop is the correct seat**, and this unit's measurement reconfirms it at a second address with a
second IDT base (`0x9C510000` now, `0x9BC04000` in the deliver unit).

**Nothing is papered over:** the port does not substitute its own fault handling for a guest fault; it
stops where the hardware would leave the architectural state entirely.

## 4. The question that remains, and its instrument

**Why is `PML4E[0]` zero at that instant, and what raised the first fault?** The watch shows only the
delivery's descriptor read — the *original* fault that started the delivery is masked by the recursion
(the bound fires before the first delivery completes). The instrument is the toolkit with the recursion
bound temporarily lifted to 1 in a debug build (or a `V86C_WATCH` on the *first* `trigger_pagefault`
address, which the ring's last entries suggest is the `rep movsq` destination `0x9C517600`). That
distinguishes "the kernel is between two table switches and its own IDT is not yet mapped" (a guest
transient, hardware resets) from "the port mis-executed the table construction" (a port defect).
