## 1. `instr64_F7_0` — TEST r/m64, imm32 (MEASURED)

    void instr64_F7_0_mem(int64_t addr, int32_t imm)   /* TEST r/m64, imm32 */
    void instr64_F7_0_reg(int32_t r1, int32_t imm)

Both over the port's existing `test64()` (`arith.c`: `test64 = arith_and(x, y, OPSIZE_64)`, i.e.
AND's flags without the store). The immediate is **sign-extended** to 64 bits, which is the SDM's
rule for a 64-bit operand; the flags are CF/OF cleared, SF/ZF/PF from the result, **AF undefined**.

**The arm** is a corpus case, `alu/test-imm32-64`:

    mov rax, -1
    test rax, 0xFFFFFFFF80000000      ; ANDs 0xFFFFFFFF80000000 -> SF=1
    mov rbx, 0x1122334455667788
    test rbx, 0xFFFFFFFF80000000

A **zero-extending** engine ANDs `0x0000000080000000` and leaves **SF=0**, so the two plausible wrong
implementations are separated by one flag; the case compares `0x8C5` so the **undefined AF** is
dropped (the corpus's own rule, `gen/nasm64_gen.py`'s `flags_mask` note). It is **RED against the
pre-fix binary** (the body was a named stop) and green now: `make nasm64` 13/0 with **all 85 cases
agreeing** against the native oracle.

**READ, and worth recording:** the interpreter generator finds bodies by **scanning the source text**,
so a body created by a macro is invisible to it. MEASURED: my first attempt used a
`DEFINE_BITTEST64` macro and the census stayed at 44 unimplemented with the new call sites emitted as
stops; writing the functions out explicitly routed them. Any future "implement N bodies" unit must
write them out.

## 3. Why this unit stops here (the brief's STOP rule)

The next stop is **not a body**: it is the fault-delivery recursion bound firing, i.e. a #PF whose
delivery faults again. That is a **walk rule / frame shape** question, not "implement the named
body", so per the brief's rule (4) it is named and left for its own unit:

**Next fork:** which access faults at `0xffffffff890ef901` and why its delivery re-enters — the
toolkit is now well suited (`V86C_CHAIN`/`V86C_BREAK_CHAIN`/`V86C_PEEK_SP`), and the 64-bit frame is
correct since `results/x86-64-kgs.md`, so the frame is no longer a suspect.
