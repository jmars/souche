# x86-64: the deterministic #GP localised — `LEAVE` was popping four bytes, and the next stop is `mov cr4` with LA57

**Status: the defect the last unit left unnamed is FOUND, FIXED and re-run as the acceptance test.
The amd64 guest now runs 2,962 instructions FURTHER and stops at a NEW, precisely named stop.**

Every claim is tagged **MEASURED** / **READ** / **INTERPRETATION** / **PROJECTION**.

## 1. Measurement (a): the stack at the tail call — the frame is right, the pop is not (MEASURED)

The three measurements the last unit named were done in one instrumented run (2m13s):

    PROBE (a) at 0x1001BD2: rbp=0x2a04000 rsp=0x2a03f2c
    PROBE   [0x2a03f28]=0x2a04000     <- the saved RBP
    PROBE   [0x2a03f30]=0x100083a     <- the RETURN ADDRESS into head_64.S
    PROBE   [0x2a03f38]=0x4780000
    PROBE   [0x2a03f40]=0x1000000
    PROBE   [0x2a03f48]=0x1000036
    PROBE   [0x2a03f50]=0x84790       <- the `pushq %rsi` of boot_params
    PROBE   [0x2a03f58]=0x0

`0x1001BD2` is the `jmp` of `leave; jmp <tail call>`, i.e. the capture is **after** `leave` ran. The
frame the stub built is intact: `pushq %rsi` put 0x84790 at 0x2a03f50, `call
startup_64_setup_env` put the return address **0x100083a** at 0x2a03f48, and the C prologue put the
frame base at **0x2a03f28** with the saved RBP at [rbp] and the return address at [rbp+8].

**The registers do not match the frame:** after `leave`, RBP = 0x2a04000 (the *saved* value, which is
right) but **RSP = 0x2a03f2c**, four bytes short of the correct 0x2a03f30. So the `ret` at 0x1E01D30
popped the qword at **0x2a03f2c** — which straddles the saved RBP and the return address:

    bytes [0x2a03f2c..0x2a03f33] = 00 00 00 00 | 3a 08 00 01   ->  0x0100083A00000000

That address is **non-canonical** (bit 48 set, bits 63:47 not all ones) → **#GP(0)** → delivered into
the NULL IDT the stub leaves (`idtr base=0 limit=0`) → the machine stops. **The frame is not wrong;
the pop is.**

## 2. The defect: `0xC9 LEAVE` had no 64-bit body (MEASURED, and FIXED)

`0xC9` is not in `long_mode_default64()`, so in 64-bit mode it dispatched to the **32-bit** arm
`instr32_C9`, which pops a **four-byte** EBP and moves the stack by 4 (`set_stack_reg(old_vbp + 4)`).
The SDM's LEAVE at 64 bits pops **eight** bytes. Four bytes short is exactly the 0x2a03f2c measured
above.

**The fix** (`src/cpu/instructions_64.c`, `instr64_C9`): RSP = RBP, then an eight-byte pop, with the
read before the write so a faulting LEAVE leaves both registers as they were (the instruction is
re-executed after the handler's `iret`). The overlay gained a **base-table** entry
`{ opcode: 0xC9, default64: true, narrow64: … }` (158 entries now), and the generated 0x2C9 arm calls
it instead of stopping.

**The arm that fails before and passes after (MEASURED):** new corpus case `ctrl/leave-64` — a frame
at 0x100800 with a 64-bit saved RBP, `leave`, then the resulting RBP and RSP stored into the compared
window. With the overlay entry reverted (so the 32-bit arm runs again):
`SUMMARY: total=81 green=80 red_unimplemented=0 mismatch=1`, `ctrl-leave-64.img: 6 field(s)`
MISMATCHED. With the fix: **81/81 green** on the long-mode leg.

## 3. The acceptance test: the guest runs further, and the next stop is named (MEASURED)

| | before the fix | after the fix |
|---|---|---|
| instructions | 4,475,477,692 | **4,475,480,654** (+2,962) |
| stop | #GP on the `ret` at 0x1E01D30 | **#GP on `mov cr4, rcx` at eip=0x10000A1** |
| idtr | base 0x0 limit 0 (the stub's NULL IDT) | **base 0x2A04000 limit 511** (the kernel's OWN bringup IDT) |
| wall clock | 112-118 s | 112 s |

The IDT changing from NULL to the kernel's own `bringup_idt_table` is the proof that
`startup_64_setup_env` **completed**: it is that function's last act (`startup_64_load_idt`).

**The next stop, with its evidence:**

    faulting rip 0x10000A1 bytes 0f 22 e1 48 03 05     ->  `mov cr4, rcx`
    rcx = 0x10a0 = PAE(0x20) | PGE(0x80) | LA57(0x1000);   old CR4 = 0x20
    idtr base=0x2a04000 limit=511, descriptor for vector 13 at 0x2a040d0 = 0x0
    cr2 = 0x0, cr3 = 0x4f76000, cpl 0

The port #GPs because it treats **CR4 bit 12 (LA57) as reserved**
(`instructions_0f.c`: `(1<<11|1<<12|1<<15|1<<16|1<<19) | 0xFFC00000`). The bit came from the kernel's
own code (MEASURED, the 48 bytes before the write):

    48 8b 04 25 f8 c8 84 8a   mov rax, [0xffffffff8a84c8f8]
    48 05 00 00 81 0a         add rax, 0x0a810000
    0f 20 e1                  mov rcx, cr4
    83 e1 40                  and ecx, 0x40            ; keep MCE
    81 c9 a0 00 00 00         or  ecx, 0xa0            ; PAE | PGE
    f7 05 d7 3c 41 01 01 00 00 00   test dword [rip+0x01413cd7], 1   ; -> 0x2143D6F
    74 06                     jz  +6
    81 c9 00 10 00 00         or  ecx, 0x1000         ; LA57   <- TAKEN
    0f 22 e1                  mov cr4, rcx

READ (`arch/x86/boot/compressed/pgtable_64.c:212-218`): that variable is `__pgtable_l5_enabled`, set
to 1 **iff `__read_cr4() & X86_CR4_LA57`** after the trampoline — and the trampoline's own CR4 write
left LA57 clear (old CR4 = 0x20 at the kernel's write), while CPUID leaf 7 ECX is **0** in the port
(no LA57 advertised, MEASURED). So the guest should have `__pgtable_l5_enabled == 0` and it does not.

**What this unit does NOT claim:** that this is a port defect. The variable is at **0x2143D6F** and it
is nonzero; *who wrote it* is not established, and the three candidate explanations (a wrong
`__read_cr4()` result at pgtable_64.c:212, a mis-executed write to that address, or the port's
`test` — whose body `instr32_F7_0_mem` was checked and is correct) were not separated.

**THE FOURTH MEASUREMENT, named and cheap (~2 min):** a watchpoint on physical 0x2143D6F — log the
first write to it with the faulting rip and the stored value, and log the result of the stub's
`mov %cr4, %rax` at pgtable_64.c:212. That distinguishes the three candidates directly. A second,
independent probe worth having at the same time: whether the port's CR4 should accept bit 12 at all
— the honest answer is **no** (the port's walk is 4-level and its physical model is 32-bit), which is
why the defect to fix will be the one that *sets* the flag, not the CR4 check.

## 4. Measurement (b): the relocation — the copy is faithful (MEASURED, with one byte unexplained)

    PROBE (b) pre@0x1200000:  48 8d 25 51 3f a0 01 48 8d 3d f2 ff ff ff b9 01 01 00 c0 48 8b 05 9e b2 bf 01 48 c7 c2 00 00 00
    PROBE (b) pre@0x1000000:  7f 45 4c 46 02 01 01 00 …                (the ELF header, still intact)
    PROBE (b) post@0x1000000: 48 8d 25 51 3f a0 01 48 8d 3d f2 ff ff ff b9 01 01 00 c0 48 8b 05 9e b2 bf 01 48 c7 c2 00 00 e0

The entry code the guest later executed at 0x1000000 (`startup_64`) is **byte-identical to the pre-copy
source at 0x1200000 for the first 29 bytes**, so `parse_elf`'s `memmove` did move the segment to its
`p_paddr` — **the relocation hypothesis is refuted for the region that matters**. Byte 29 differs
(`00` vs `e0`); the instruction it belongs to is `48 c7 c2 <imm32>` (`mov rdx, imm32`) whose expected
immediate is `_text`'s low half, and the discrepancy is **recorded, not explained** — a fourth
candidate for the next unit, since it is a single byte in the destination and not in the source.

## 5. Measurement (c): the program headers — the capture was taken too late (MEASURED, and the
capture is corrected here)

The 500 M-instruction capture read **garbage** (`phdr0 type=1221281872`). The header itself was
**intact at both 300 M and 500 M**:

    PROBE (c) header@0x1000000 at 300M: 7f 45 4c 46 02 01 01 00 00 00 00 00 00 00 00 00
    PROBE (c) header@0x1000000 at 500M: 7f 45 4c 46 02 01 01 00 00 00 00 00 00 00 00 00

so the phdrs at `0x1000040` were being read at the wrong offset, not overwritten — `e_phoff` was not
re-measured in that run, and the earlier unit's `e_phoff = 0x40` reading came from a different
capture. **The honest state: the program-header table was NOT successfully decoded before
`parse_elf`; (b) answers the relocation question without it** (the entry code matches its source), and
the correct capture is a re-measurement, not an inference.
